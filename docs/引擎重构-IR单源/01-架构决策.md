# 01 · 架构决策（ADR 性质）

状态：**已确认（authoritative）**
日期：2026-06-28
决策范围：MQL 策略引擎的执行与分析拓扑

---

## 1. 背景

平台目标：让用户上传任意 MQL4/MQL5 EA，在**服务端**完成 paper / live / backtest 执行，并提供导入前的"覆盖度/盲区"报告以建立用户信心。

行情与下单的唯一通道是 mtapi（`/opt/ant/reference/grpc/mt4.proto`、`mt5.proto`）。

## 2. 关键事实（已核实）

### 2.1 mtapi 不能托管 EA

`mt4.proto` 暴露的 service 仅为：

- `Connection`：Connect / ConnectEx / Disconnect
- `MT4`（只读）：AccountSummary / Quote / OpenedOrders / OrderHistory / QuoteHistory …
- `Subscriptions`（推送）：Subscribe / SubscribeOrderProfit / SubscribeTickValue / SubscribeOrderUpdate
- `Trading`：OrderSend / OrderClose / OrderModify …

**没有任何 `RunExpert` / `LoadEA` / `ExecuteMQL` 类 RPC。** mtapi 是无头交易桥，不是 EA 宿主。

**推论**：要在本设施上运行任意 MQL，唯一物理路径是——服务端运行策略逻辑，把决策翻译成 mtapi 的 `OrderSend/OrderModify/OrderClose`。**"服务端自主执行"不是选择，是被接口面强制的。** 不存在更高保真的替代方案。

### 2.2 当前存在两套互相分裂的 MQL 引擎

| | 引擎 A：识别器 + 转译器 | 引擎 B：解释器 |
|---|---|---|
| 入口 | `mql2go.Analyze` → `StrategyIntent` | `mql2go.CompileToIR` → `interp.IR` |
| 产物 | 高层规则（Entry/Exit/Indicator）→ `Generate` 出 Go 源码 | 语句级可执行 IR |
| 保真度 | **有损**（仅识别枚举过的模式，其余为盲区） | **全保真**（函数/全局/类/枚举/表达式全量） |
| 失败模式 | **静默跳过**（盲区 = 少下单/风控失效，危险） | **显式报错**（未知 builtin → NoneVal + log，可见） |
| 谁在用 | 前端导入 UI 的报告 + 部分执行路径 | live / backtest 运行时 |

致命点：`StrategyIntent`（识别器产物）**同时**被用于"给用户看的报告"和"喂给 gen.go 的执行路径"，而 `interp.IR` 是另一套完全独立的表示。于是**用户看到的覆盖度报告永远不等于实际执行行为**——这不是 bug，是拓扑决定的必然。

## 3. 决策

### 3.1 核心结论

> **`interp.IR` 是 MQL 策略的唯一权威表示（single source of truth）。**
> 执行、覆盖度报告、Go 导出三者全部从同一个 `interp.IR` 派生。
> 有损的模式识别器（`StrategyIntent` / `mql2go.Analyze`）从**执行**与**报告**路径上彻底剥离。

### 3.2 三个派生消费者

```
                         MQL 源码（事实源，入库保存）
                              │
                        tree-sitter CST
                              │
                              ▼
        ┌────────────  interp.IR（唯一权威表示）────────────┐
        │                     │                              │
        ▼                     ▼                              ▼
   解释器执行            IR 静态分析                    Go 生成器
  (live + backtest)   (覆盖度/盲区/参数)              (可选导出/阅读)
   【主执行后端】       【UX，与执行同源】              【旁路，不进执行】
```

### 3.3 盲区的正确定义

盲区 ≠ 识别器没匹配到的模式。

> **盲区 = `interp.IR` 中出现、但解释器 `builtinTable` / `switch` 未实现的 builtin/API 调用。**

它是遍历"与执行完全相同的 IR"得出的，因此**报告里标红的，运行时一定显式失败；报告里说支持的，运行时一定按该语义执行**。分歧从拓扑上消除。

### 3.4 必须保留的正交路径

**Go 原生执行路径（`goExecutor` / `isGoStrategy`）不得删除。** 它服务于 AI 生成的原生 Go/SDK 策略（`AIStrategyTemplate.CodeSkeleton` 即 Go 源码）。

本次重构只切除 **MQL → gen.go（有损）→ 执行** 这一条分叉。最终两条正交执行路径：

- **MQL 策略** → `CompileToIR` → 解释器（权威，全保真）
- **原生 Go/SDK 策略** → `goExecutor`（保留）

### 3.5 事实源是原始 MQL，不是 IR、更不是 gen.go 的 Go 输出

IR 是派生产物，可随解释器演进重新编译。**入库保存原始 MQL 文本 + 来源语言 + 提取的参数**；运行时从原始 MQL 重新 `CompileToIR`。gen.go 的 Go 输出仅作"导出阅读"，绝不作为执行或持久化的事实源。

### 3.6 版本感知（MT4 / MT5）

MT4 与 MT5 的交易 API 完全不同且不可混用。本设计在三个层面区分版本，施工方必须遵守：

**(a) 版本检测在 IR 之上游、已完成。**
`mql2go.detectMQLVersion` 在 `CompileToIR` 时把 `"mql4" | "mql5"` 写入 `IR.Version`。所有下游消费者（解释器、静态分析、导出）以 `IR.Version` 为准，**不得各自重新猜版本**。

**(b) 调用形态按版本不同——这是 Task 1 的致命正确性点。**

| 维度 | MQL4 | MQL5 |
|------|------|------|
| 下单 | 自由函数 `OrderSend(...)` → `ExprCall` | 类方法 `trade.Buy(...)` → `ExprField` → `dispatchClassMethod` |
| 持仓模型 | 订单池 `OrderSelect` + `OrdersTotal` 遍历（`MQL4OrderPool`） | 仓位池 `PositionsTotal` + `PositionGetTicket`（`MQL5PositionPool`） |
| 改单/平仓 | `OrderModify` / `OrderClose` | `CTrade.PositionModify` / `PositionClose` |
| 属性读取 | `OrderStopLoss()` 等 Order* | `PositionGetDouble/Integer/String` |

> **静态分析（Task 1）必须同时遍历 `ExprCall` 与 `ExprField` 方法调用。** 若只遍历 `ExprCall`，MT5 的全部交易调用（`CTrade.Buy` 等）会对覆盖度隐形，产出虚假的 100% 覆盖——这是最危险的误判。

**(c) 盲区严重度与"期望 builtin 集"按版本判定。**
缺失 `PositionGetDouble` 对 MQL5 是致命、对 MQL4 无意义；缺失 `OrderSelect` 反之。Task 0 的覆盖矩阵、Task 1 的严重度分类都必须按 `IR.Version` 分列。

**(d) 适配器不共享规则的适用范围——重要澄清。**
AGENTS.md "MT4 和 MT5 adapters MUST NOT share code" 约束的是 **`adapter/mt4/` 与 `adapter/mt5/`（mtapi 网关层）**。

> **解释器（`tools/mql2go/interp/`）是语言运行时，不是 broker 适配器。** 它合理地在同一套代码中处理 MQL4 与 MQL5 两种方言（按 `IR.Version` 与调用形态分派），再把交易决策经 `sdk.Broker` 抽象统一路由出去。**施工方不得**以"MT4/MT5 不共享"为由把解释器拆成两份——那是对规则范围的误用。解释器内部已用 `callTrade`（含两版函数）、`execCTrade`（MQL5 类方法）、`MQL4OrderPool`/`MQL5PositionPool` 做了正确的方言区分。

## 4. 被否决的替代方案

| 方案 | 否决理由 |
|------|---------|
| 原生 MT 终端执行（卸载给 mtapi） | mtapi 无 EA 托管能力（§2.1），物理上不存在 |
| gen.go 转译器作为执行引擎 | 模式识别对任意 EA 必然有损；静默跳过对交易是危险的（§2.2） |
| 维持双引擎，仅修对接 | 预览与执行的分歧是拓扑必然，治标不治本 |
| 以 IR 为持久化事实源 | IR 是派生物；解释器演进会使旧 IR 失真。应存原始 MQL（§3.5） |
| LLM 翻译作为主执行路径 | 非确定、不可验证。保留为盲区兜底，不作主路径 |

## 5. 唯一真实变量

解释器的 builtin/指标覆盖度。这是**实现进度**问题，不动摇架构方向，且 IR 单源使缺口**可见、可度量、可逐个补齐**（实现一个 builtin 处处生效）。见 `02-施工工单.md` Task 0。
