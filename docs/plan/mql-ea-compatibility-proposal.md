- ❌ 不执行 DLL
- ❌ 不执行编译好的 .ex4/.ex5
- ❌ 平台不集成 MT4/MT5 终端（生产环境不依赖终端运行）

## 1. 问题陈述

我们的自研 VM 重新实现了 MQL 运行时（常量表 428 行、~200 个内置函数、~40 个指标）。每当用户 EA 碰到没实现的常量/函数/行为，就产生**静默错误**（如 `MODE_SIGNAL` 缺失 → iMACD 返回错误线 → 永不开单）。

两个核心问题：
1. **AI 能帮什么？** — 在自研 VM 不完善的前提下，AI 如何加速补全和验证
2. **如何自主发现 + 自我进化？** — 系统如何自动发现问题、修复问题、持续提升

## 2. v3 方案的致命缺陷

v3 假设"编译失败 → AI 修改 `constants.go` → 重新编译 Go → 重新回测"可以在用户请求中实时完成。但生产环境中：

- `constants.go`、`vm_builtin_*.go` 是编译好的 Go 二进制，运行在 Docker 容器里
- AGENTS.md 明确禁止容器内 `go build`、禁止 `docker cp` 宿主机二进制
- Docker rebuild + redeploy 需要 minutes，不可能在用户回测请求里做
- AI 生成函数实现 + 编译 + 测试更不可能实时完成

**结论**: v3 的"自动修复循环"对值映射错误、函数缺失**在生产环境无法实时执行**。

## 3. 最优解：分层修复 + 两个循环

### 3.1 关键洞察：常量表可以运行时扩展

MQL 常量（如 `MODE_SIGNAL=1`）是**数据**，不是**代码**。如果把常量表从 Go 硬编码改为**运行时可加载的映射**（从 DB 读取），那么：

- AI 检测到 `MODE_SIGNAL` 缺失 → 推断值为 1 → 写入 DB 常量表
- MQL → Bytecode 编译器在每次回测请求时都重新运行，新常量立即生效
- **不需要 Docker rebuild**，因为 Go 二进制没变，变的是运行时数据

这使得**常量缺失这类最常见的问题可以在用户请求中实时修复**。

### 3.2 修复能力的分层

| 问题类型 | 能否运行时修复? | 修复方式 | 需要重启? |
|----------|---------------|---------|----------|
| **常量缺失** | 是 | AI 推断值 → 写入 DB 常量表 → 重新编译 MQL | 否 |
| **函数未实现** | 否 | AI 生成 Go 代码 → Docker rebuild | 是 |
| **值映射错误** | 否 | AI 诊断 → 修正 Go 代码 → Docker rebuild | 是 |
| **指标算法差异** | 否 | AI 生成修正 → Docker rebuild | 是 |
| **交易行为差异** | 否 | AI 生成修正 → Docker rebuild | 是 |

### 3.3 两个循环

```text
快循环（运行时，用户请求内）:
  编译 MQL → 常量缺失?
    → AI 推断常量值 → 写入 DB 常量表 → 重新编译 MQL
    → 循环直到编译通过或常量修复穷尽
  回测 → 结果异常?
    → AI 诊断 → 如果根因是常量 → 快循环修复 → 重新回测
    → 如果根因是代码 bug → 进入慢循环

慢循环（离线，版本发布间）:
  AI 生成 patch（函数实现/值映射修正/指标算法）
    → 开发者 review → 合并 → Docker rebuild → 部署
    → 下次用户回测时自动生效
    → 同时更新知识库 + 回归测试
```

### 3.5 运行时常量表架构

**当前**: `constants.go` 硬编码所有常量值

```go
var constants = map[string]int64{
    "MODE_MAIN":  0,
    "MODE_SIGNAL": 1, // 如果缺失就 push 0
    ...
}
```

**改为**: 编译时从 DB 加载常量

```go
// 启动时加载内置常量 (constants.go)
// + 从 DB 加载运行时补充常量 (mql_runtime_constants 表)
// 合并后作为编译器的常量查找表

type ConstantTable struct {
    builtin map[string]int64    // 编译进二进制的常量
    runtime map[string]int64    // 从 DB 加载的运行时常量
}

func (ct *ConstantTable) Lookup(name string) (int64, bool) {
    if v, ok := ct.runtime[name]; ok {
        return v, true
    }
    if v, ok := ct.builtin[name]; ok {
        return v, true
    }
    return 0, false
}
```

**DB 表**:

```sql
CREATE TABLE mql_runtime_constants (
    name        TEXT PRIMARY KEY,
    value       BIGINT NOT NULL,
    mql_version SMALLINT NOT NULL,  -- 4 or 5
    source      TEXT NOT NULL,       -- 'ai_inferred' / 'manual' / 'imported_from_mqh'
    confidence  REAL DEFAULT 1.0,    -- AI 推断的置信度
    created_at  TIMESTAMPTZ DEFAULT NOW()
);
```

**AI 写入流程**:

1. 编译器遇到未知常量 `MODE_SIGNAL` → 报错
2. 管线调用 AI："MQL4 常量 MODE_SIGNAL 的值是多少？"
3. AI 从 MQL 文档知识推断：`MODE_SIGNAL = 1`
4. 写入 `mql_runtime_constants` 表
5. 重新编译 MQL（使用更新后的常量表）
6. 编译通过 → 继续回测

## 4. AI 的三个角色

### 4.1 运行时 AI：常量推断器（快循环）

**触发**: 编译 MQL 时遇到未知常量

**输入**: 常量名 + MQL 版本 + EA 源码上下文

**输出**: 常量值 + 置信度

**约束**:

- 只处理常量推断，不处理函数/逻辑
- 低置信度（< 0.8）的推断标记为 warning，不自动写入
- 每个推断记录到 DB，可追溯

### 4.2 运行时 AI：回测诊断器（快循环）

**触发**: 回测结果异常

**输入**: EA 源码 + blind spots + 回测结果 + 已知 pitfall 知识库

**输出**: 根因 + 修复建议 + 是否可运行时修复

**约束**:

- 如果根因是常量 → 触发常量推断器 → 重新回测
- 如果根因是代码 bug → 生成诊断报告 → 展示给用户 + 进入慢循环

### 4.3 离线 AI：VM 工匠（慢循环）

**触发**: 慢循环批量处理（如每日/每周）

**输入**: 所有待修复的诊断报告 + VM 源码

**输出**: Go 代码 patch + 测试 + runbook 更新

**约束**:

- 生成的代码必须通过测试
- 交易逻辑改动需要人工 review
- 常量从 DB 同步回 `constants.go`（作为 builtin，不再依赖运行时加载）

## 5. 审计报告：何时展示给用户

### 5.1 不展示给用户的情况

- 常量缺失已被 AI 运行时修复 → 用户无感
- 回测结果正常，blind spots 为空 → 无需展示

### 5.2 展示给用户的情况

- 常量修复后回测仍异常（说明有更深层问题）
- 存在未实现函数（blind spots 非空）
- 值映射错误等代码 bug（需要等慢循环修复）
- AI 无法确定根因

### 5.3 审计报告内容

```text
回测结果
  交易数: 0
  净收益: $0

兼容性报告
  ⚠ 检测到 2 个问题：

  1. [已自动修复] MODE_SIGNAL 常量缺失
     → AI 已推断 MODE_SIGNAL=1 并自动补全
     → 回测已使用修正后的常量重新执行

  2. [待修复] OrderType() 返回值映射错误
     → OrderType() 返回 1/-1 但 EA 期望 0/1
     → 持仓管理逻辑可能失效
     → 预计在下个版本修复
     → 建议: 当前回测结果中平仓逻辑可能不准确

  是否继续查看回测结果？
```

### 5.4 内部知识库（不给用户看）

- 每次诊断的根因、修复方案、pitfall 模式
- 存入 `docs/runbook/mql2go-known-pitfalls.md` + DB
- 下次遇到同类问题，AI 直接从知识库匹配

## 6. 自我进化闭环

### 6.1 快循环进化

每次 AI 成功推断常量 → 写入 DB → 下次同类 EA 直接命中，不需要 AI 介入。

```text
第 1 个用户提交含 MODE_SIGNAL 的 EA
  → AI 推断 MODE_SIGNAL=1 → 写入 DB

第 2 个用户提交含 MODE_SIGNAL 的 EA
  → DB 已有 MODE_SIGNAL=1 → 直接编译通过，无需 AI
```

### 6.2 慢循环进化

每次离线 AI 生成 patch 并合并后：

```text
AI 生成 patch → 测试通过 → 合并代码
  → 添加回归测试 (防止回退)
  → 更新 runbook (记录新模式)
  → 将运行时常量同步到 constants.go (成为 builtin)
  → Docker rebuild → 部署
  → 下次用户回测时自动生效
```

### 6.3 知识积累机制

| 知识类型 | 存储位置 | 更新触发 | 用途 |
|----------|---------|---------|------|
| 运行时常量 | `mql_runtime_constants` 表 | AI 实时推断 | 快循环修复 |
| 已知 pitfall | `docs/runbook/mql2go-known-pitfalls.md` | 慢循环修复后 | AI 诊断时匹配 |
| 诊断记录 | DB (诊断报告表) | 每次异常诊断 | 慢循环批量处理 |
| 回归测试 | `vm_test.go` / `e2e_test.go` | 慢循环修复后 | 防止回归 |
| EA 测试库 | `testdata/` | 每次发现新 EA 模式 | 持续扩大覆盖 |

## 8. 关键设计原则

1. **分层修复**: 常量运行时修（快），代码 bug 离线修（慢），不混为一谈
2. **快循环优先**: 能在运行时修的先修，修不了的才进入慢循环
3. **Go 代码检查优先于 AI**: 能用 Go 代码确定性检查的，不用 AI
4. **审计报告分层展示**: 已修复的不展示，待修复的展示 + 说明影响
5. **同一类问题只出现一次**: 快循环常量写入 DB 后永久生效；慢循环修复后同步到 builtin + 回归测试
6. **用户无感是目标**: 理想情况下用户不知道有过问题——常量已自动补全，回测结果正确

## 9. 待讨论决策点

### Q1: 运行时常量推断的置信度阈值?

- AI 推断常量值时，置信度 > X 才自动写入 DB
- 低于 X 的标记为待确认，展示给用户
- **推荐**: 阈值 0.9，MQL 常量值通常是确定性的整数

### Q2: 未实现函数的回测策略?

- **拒绝回测**: 严格，但可能阻断部分可用的 EA
- **允许回测 + 标记**: 函数返回 0，标记 blind spot，回测结果可能不准确
- **推荐**: fatal 级别（交易相关）拒绝，warning 级别（显示相关）允许 + 标记

### Q3: 慢循环的触发频率?

- **每日**: 批量处理前一天的诊断报告
- **每周**: 开发者集中处理
- **按需**: 诊断报告积累到一定数量时触发
- **推荐**: 每日自动触发 + 开发者按需处理

### Q4: 审计报告展示形式?

- **回测结果页内嵌**: 在回测结果下方展示兼容性报告
- **弹窗**: 回测完成后弹窗提示
- **聊天消息**: 在 AI Chat 中展示
- **推荐**: 回测结果页内嵌，已修复问题折叠，待修复问题展开

### Q5: 运行时常量 vs builtin 常量的同步?

- 运行时 AI 推断的常量先写入 DB
- 慢循环时将高置信度常量同步到 `constants.go` (成为 builtin)
- 下次 Docker rebuild 后，该常量不再依赖 DB
- **推荐**: 自动同步，DB 常量作为 builtin 的前置缓存

## 10. 架构方向评估：mql2go 是否走错了方向？

### 10.1 三条可选路径对比

在当前约束下（不执行 .ex4/.ex5、不用 MT 终端、只用 mtapi.io），有三条路：

| 路径 | 能跑什么 | 需要维护什么 | 核心问题 |
|------|---------|------------|---------|
| **语义提取**（旧 recognizer） | 简单 EA（if/else + 指标 + OrderSend） | 规则提取器 | 复杂 EA 直接放弃，覆盖率低 |
| **转译到 Go/Python** | 理论上所有 EA | 转译器 + MQL 内置函数 | 仍需实现所有内置函数，同样有完整性问题 |
| **自研 VM**（当前） | 理论上所有 EA | VM + MQL 内置函数 | 完整性问题是无限的 |

**关键结论**: 三条路都需要解决同一个问题——**MQL 标准库的完整性**。不管转译还是 VM 执行，`iMACD(NULL,0,12,26,9,PRICE_CLOSE,MODE_SIGNAL,0)` 都需要知道 `MODE_SIGNAL=1`、`PRICE_CLOSE=0`，并实现 iMACD 信号线计算。除非用 MetaEditor 编译 + MT 终端执行——但已排除。

**没有一条路能绕过这个问题。**

### 10.2 真正的问题不是架构，是实现策略

当前架构的三个问题都是**实现层面的**，不是架构方向选错：

**1. 静默失败是 bug，不是设计**

`compile_expr.go` 对未知常量 push 0 是偷懒的实现。正确做法是报错。这不是架构选错了，是实现时没做对。

**2. 完整性问题是所有方案的共同问题**

MetaQuotes 用了 15 年开发 MQL 运行时。我们不可能 100% 复刻。但：

- 80% 的 EA 用 20% 的 MQL 功能
- 这 20% 是有限的、可枚举的、可优先实现的
- 关键是让剩下的 80% 功能**明确报错**而不是**静默错误**

**3. 缺乏反馈循环**

当前系统的问题不是"VM 跑不了某些 EA"，而是"VM 跑不了某些 EA 但用户不知道为什么"。v4 方案的快循环/慢循环就是解决这个问题的。

### 10.3 什么时候应该考虑换方向？

如果出现以下情况，说明 VM 方向确实不对：

- 用户提交的 EA 中 >50% 都无法正确回测（说明覆盖率太低）
- 大部分 EA 的失败原因不是常量/函数缺失，而是**语义行为差异**（如 SimBroker 的成交逻辑和真实 MT 不一致）
- AI 推断常量的准确率很低（说明 MQL 常量不是确定性的，需要更深的运行时上下文）

但目前已知的问题（`MODE_SIGNAL` 缺失、`OrderType` 映射错误）都是**具体的、可修复的 bug**，不是架构性缺陷。

### 10.4 诚实的评估

**VM 方向是对的，但需要接受一个现实：我们做的是 80% 方案，不是 100% 方案。**

- 简单 EA（指标 + 条件 + OrderSend）：可以做到高覆盖率
- 中等 EA（OrderSelect 循环 + 持仓管理 + 多指标组合）：可以做到大部分覆盖
- 复杂 EA（自定义指标 DLL 调用、复杂类继承、Chart 操作）：可能永远不支持

关键是在**不支持的时候明确告诉用户**，而不是静默给出错误结果。这正是 v4 方案要做的事。

### 10.5 如果重来，会做什么不同？

如果从零开始，会在架构层面做两个改变：

**1. 常量表从一开始就是运行时加载的**，不是硬编码在 Go 里。这样 AI 补全常量不需要 rebuild。

**2. 编译器从一开始就对未知标识符报错**，不是 push 0。静默失败是最坏的设计。

但这两个改变都是**实现策略**的改变，不是**架构方向**的改变。VM + SimBroker + mtapi.io 的整体架构是合理的。

## 11. 无 LLM 方案：确定性方法替代 AI

### 11.1 问题分析

v4 方案引入 LLM 的两个场景：

1. **常量推断**：编译时遇到未知常量 → LLM 推断值
2. **根因诊断**：回测异常 → LLM 推理根因

但 LLM 有两个问题：

- **成本**：token 给少了用户不够用，给多了营运成本有压力
- **可靠性**：LLM 推断有幻觉风险，MQL 常量值必须 100% 准确

### 11.2 确定性替代方案

#### 常量：从 .mqh 头文件提取，不用 AI 推断

MQL 常量**不是无限的**，它们全部来自 MetaQuotes 发布的标准头文件（`.mqh`）：

- MQL4: `stdlib.mqh`, `error_description.mqh`, `WinUser32.mqh` 等
- MQL5: `Trade/Trade.mqh`, `Indicators/IndicatorExtensions.mqh` 等

这些头文件中所有常量都是 `#define` 或 `enum` 定义，**可以用 tree-sitter 直接解析提取**（我们已经有 MQL tree-sitter 解析器）。

**方案**:

```text
一次性导入（开发时，不是运行时）:
  1. 下载 MetaQuotes 官方 .mqh 头文件集
  2. 用 tree-sitter 解析所有 #define 和 enum
  3. 提取常量名 → 值映射
  4. 写入 constants.go（编译进二进制）
  5. 写入 mql_runtime_constants 表（运行时可扩展）

结果: 一次性覆盖 99% 的 MQL 常量，零 LLM 成本
```

**剩余 1%**（用户自定义 `#define`）由预处理器的 `#define` 处理已经覆盖——`preprocess.go` 已经实现了 `#define` 替换。

**结论**: 常量问题根本不需要 LLM。需要的是一次性系统性导入 + 编译器报错（不静默 push 0）。

#### 根因诊断：规则匹配，不用 AI 推理

回测异常的根因诊断可以做成**确定性规则引擎**：

```text
规则库（Go 代码实现，不需要 LLM）:

规则 1: 零交易 + EA 含 OrderSend/Buy/Sell
  → 检查: 编译时 blind spots 是否包含交易相关函数?
  → 检查: 运行时 blind spots 是否非空?
  → 检查: EA 入场条件依赖的指标是否已实现?
  → 输出: "交易函数 X 未实现" 或 "指标 Y 返回 0 (stub)"

规则 2: 零交易 + EA 含 iMACD + MODE_SIGNAL
  → 检查: constants 表是否有 MODE_SIGNAL?
  → 输出: "MODE_SIGNAL 常量缺失，iMACD 信号线获取错误"

规则 3: 回测有交易但持仓管理异常
  → 检查: EA 含 OrderType() 比较?
  → 检查: builtinOrderType 返回值是否与 OP_BUY/OP_SELL 一致?
  → 输出: "OrderType() 值映射可能错误"

规则 4: blind spots 非空
  → 列出所有 blind spots
  → 按严重度分类 (fatal/warning)
  → 输出: "函数 X 未实现 (fatal)，回测结果不可靠"
```

**规则库的来源**:

- 已知 pitfall（`docs/runbook/mql2go-known-pitfalls.md`）
- 每次 EA 失败后开发者分析根因 → 写成新规则
- 规则是 Go 代码，不是 LLM prompt

**规则 vs LLM**:

| 维度 | 规则匹配 | LLM 推理 |
|------|---------|---------|
| 成本 | 零 | 每次请求消耗 token |
| 可靠性 | 100% 确定性 | 有幻觉风险 |
| 覆盖率 | 只覆盖已知模式 | 可推理未知模式 |
| 维护 | 需要开发者添加规则 | 自动 |
| 速度 | 毫秒级 | 秒级 |

**结论**: 对于已知 pitfall（当前的主要问题），规则匹配足够。对于全新未知问题，规则匹配无法发现——但 LLM 也不一定可靠。不如先做规则匹配，积累失败案例，开发者分析后补充规则。

### 11.3 无 LLM 的完整管线

```text
用户点击"回测"
    │
    ▼
阶段 1: 编译
    │
    CompileMQL(source, constantTable)
    │
    ├─ 成功 → 进入阶段 2
    │
    └─ 未知常量/函数
         │
         ├─ 未知常量 → 编译错误（明确报错，不静默 push 0）
         │   → 检查 .mqh 常量表是否有该常量
         │   → 有 → 说明预处理未正确展开，修复预处理器
         │   → 无 → 拒绝编译，提示用户该常量不支持
         │
         └─ 未知函数 → 记录为 blind spot
              → fatal 级别 → 拒绝编译
              → warning 级别 → 继续编译，标记风险
    │
    ▼
阶段 2: 回测执行
    │
    Engine.Run() → Result{Trades, Equity, BlindSpots}
    │
    ▼
阶段 3: 结果验证（规则引擎，无 AI）
    │
    异常检测 (Go 代码):
      • EA 有 OrderSend 但 0 笔交易?
      • 运行时 blind spots 非空?
      • 回测有 error 日志?
    │
    ├─ 结果正常 → 返回结果
    │
    └─ 结果异常 → 规则引擎匹配
         │
         ├─ 匹配到已知规则 → 输出诊断 + 建议
         │   → 展示给用户（回测结果页内嵌）
         │
         └─ 未匹配到规则 → 记录到失败案例库
              → 展示 blind spots + 回测结果给用户
              → 开发者后续分析 → 补充规则
```

### 11.4 无 LLM 的自我进化

```text
进化循环（无 LLM）:

  用户提交 EA → 编译/回测失败
    → 记录失败案例到 DB（EA 源码 + blind spots + 回测结果）
    → 开发者定期 review 失败案例
    → 分析根因
    → 修复（补常量/补函数/修映射）
    → 添加回归测试
    → 更新规则库
    → Docker rebuild → 部署
    → 下次同类 EA 自动通过
```

**与 LLM 方案的对比**:

| 维度 | 无 LLM | 有 LLM (v4) |
|------|--------|-------------|
| 常量补全 | 一次性 .mqh 导入，覆盖 99% | 运行时 AI 推断，有幻觉风险 |
| 根因诊断 | 规则匹配，只覆盖已知模式 | AI 推理，可覆盖未知模式 |
| 修复速度 | 慢（需开发者介入） | 快（常量可自动，代码需开发者） |
| 营运成本 | 零 | token 成本 |
| 可靠性 | 高（确定性） | 中（LLM 幻觉） |
| 未知问题发现 | 依赖开发者 review | AI 可推理，但不一定准确 |

### 11.5 推荐策略：无 LLM 为主，LLM 为可选增强

**核心系统不依赖 LLM**:

1. 常量：一次性 .mqh 导入 + 运行时常量表（DB 存储，可手动追加）
2. 编译器：未知标识符报错
3. 诊断：规则引擎
4. 进化：开发者 review 失败案例 → 补充规则和实现

**LLM 作为可选增强**（不作为系统依赖）:

- AI Chat Agent 回答用户"为什么失败"时，可以调用 LLM 生成更友好的解释
- 离线分析时，开发者可以选择用 LLM 辅助分析复杂失败案例
- 这些都是**锦上添花**，不是**系统必需**

**好处**:

- 零营运成本（不依赖 LLM token）
- 高可靠性（确定性规则 + 确定性常量）
- 系统始终可用（不依赖外部 API）
- LLM 成本可控（只在需要时用，不是每次回测都用）

### 12.0 三个基石判断

**基石 1：MQL API 是封闭集合，"自我识别"可以做成查表而不是推断。**
MQL4/MQL5 的全部函数（各约 700 个）、常量、枚举都在 MetaQuotes 官方文档中，是有限、已发布、可一次性枚举的。识别问题的正确解法不是"运行时猜"，而是**枚举整个 API 面，消灭 unknown unknowns**。

**基石 2：语义偏差没有真值预言机，标准解法是差分测试 + 蜕变测试。**
"实现了但行为和 MT4 不一致"这类问题，在不能跑 MT 终端的约束下没有 ground truth。测试学界对无预言机问题的标准答案：
- **差分测试**：指标输出和独立参考实现对拍（同一数据下我们的 iMACD vs 独立计算的 `EMA(12)−EMA(26)` 及其 EMA(9) 信号线）——本次 MODE_SIGNAL 事故会被这一层直接抓住
- **蜕变测试**：不依赖任何实现的恒等式（`iMA(period=1) ≡ price`、`平仓盈亏 ≡ (close−open)×lots×tickvalue×方向`、`iHighest 返回的 bar 的 High ≥ 区间内所有 High`）——OrderType 映射错误会导致持仓恒等式破裂，被这一层抓住

**基石 3：回测引擎在生产环境绝不自改执行语义；AI 的正确位置是"有确定性验证器的代码合成"。**
这是碰钱的系统，运行时自修复执行语义 = 不可审计的风险。AI 参与修复的唯一正确形态：**慢循环里 AI 生成 patch + 测试 → 确定性测试台（回归 + 差分 + 蜕变）裁决 → 人只 review 合并**。LLM 有 verifier 兜底时，幻觉不会进入生产；没有 verifier 的 AI 修复（如运行时常量推断）一律不做。

### 12.1 架构：四层

```text
Layer 0  封闭世界 API 注册表（消灭 unknown unknowns）
─────────────────────────────────────────────────────
  一次性从 MQL4/MQL5 官方文档+头文件枚举全部符号 →
  api_registry（Go 生成代码，进仓库）：
    每个符号 ∈ {implemented, stubbed, unsupported} 三态，无第四态
  CI 不变量：VM builtinRegistry ∪ constants 与注册表 1:1 对账，
    出现注册表外的符号引用或无状态符号 → CI 失败
  编译器行为由状态驱动：
    implemented → 正常编译
    stubbed     → 编译通过 + 兼容性报告声明影响（显示类函数等）
    unsupported → 拒绝编译，明示符号名和原因（DLL 调用等）
    查无此符    → 编译错误（用户拼写错误或注册表缺口，各自明示）

Layer 1  三层探测（全部确定性，零 LLM）
─────────────────────────────────────────────────────
  D1 编译期：符号状态检查（Layer 0 驱动，覆盖率 100%）
  D2 运行期：stub 调用遥测 + 规则引擎
     （零交易+含 OrderSend、指标恒返 0、error 日志 → 命中规则输出诊断）
  D3 语义层：nightly CI 跑差分指标对拍 + 蜕变恒等式 + EA 语料库回归
     （抓"实现了但不对"的问题，本次两个 bug 都属于这层能抓的类型）

Layer 2  修复分速（按可验证性分层，不按紧急度）
─────────────────────────────────────────────────────
  预防（一次性）：常量/枚举全量导入，符号注册表建立
  自动诊断（实时）：失败签名 =（命中符号集, 命中规则, 恒等式破裂点）
     → 去重聚类 → 自动生成复现包（EA hash + 最小数据窗 + 期望差异）
  AI 修复（慢循环，日批）：复现包 + VM 源码 → AI 生成 patch + 回归测试
     → 确定性测试台裁决（全语料库 + 差分 + 蜕变必须全绿）
     → 人 review 合并 → docker compose build 部署
  人工兜底：AI 三次不过测试台 → 转人工，复现包已备好

Layer 3  进化飞轮（数据驱动优先级）
─────────────────────────────────────────────────────
  每个失败 EA（匿名化）→ 语料库 testdata/ → 永久回归
  失败签名频次加权 → 缺口 backlog（先修阻塞最多用户的符号/行为）
  北极星指标：用户 EA 首次回测成功率，按版本追踪
  修复后：注册表状态翻转 + 回归测试 + runbook 模式沉淀
```

### 12.2 为什么这比 v4/v5 更优

| 维度 | v4（运行时 AI） | v5（无 LLM） | 本方案 |
|------|---------------|-------------|--------|
| 未知符号发现 | 碰到才知道 | 碰到才知道 | **注册表穷举，编译期 100% 覆盖** |
| 语义偏差发现 | AI 猜根因 | 规则匹配已知模式 | **差分+蜕变，抓未知模式且确定性** |
| 修复速度 | 常量实时/代码慢 | 全人工 | **诊断自动化+AI 产 patch，人只 review** |
| AI 幻觉风险 | 直接进生产 | 无 AI | **测试台 verifier 兜底，幻觉进不了生产** |
| 进化方向 | 无优先级 | 开发者直觉 | **失败频次加权，修影响面最大的** |

v5 的规则引擎只能匹配已知模式——但本次事故恰恰是"未知模式"（没人知道 MODE_SIGNAL 缺失前它是问题）。差分/蜕变测试不需要预知模式，只需要恒等式成立，这才是抓未知问题的确定性手段。

**砍掉（维持前版结论）**：❌ `mql_runtime_constants` DB 表（双源常量违背单一事实源，注册表进 Go 代码单源）；❌ 运行时 AI 常量推断（概率模型推断确定性事实，方向错误）。
**修正前版一处**：离线 AI patch 管线**不砍了，改造为"AI 产出 + 测试台裁决"**——前版砍它是因为"无 verifier 的 AI 修复不可信"，本方案的测试台恰好补上了 verifier，AI 修复变得可审计。但仍按量级触发：失败签名 backlog ≥ 每周 5 个新模式才启动自动化，此前人工修（复现包已自动备好，修复成本已大幅降低）。

### 12.3 执行分三批

### 12.4 MT 对拍基准（parity benchmark）与"推倒重来"裁决

**推倒重来：否决。** 管线 = 20% 架构件（解析器/编译器/VM）+ 80% 语义件（内置函数/指标/SimBroker/常量）。语义件在任何替代架构中一行省不掉，重写只是扔掉能工作的 20% 再面对同样的 80%，收益为负。重新评估的触发条件维持 §10.3 三条，目前一条未命中。

**与 MT 客户端的差异，测出来而不是猜**（REUSE: `strategy/backtest/parity_test.go` 已能解析 MT4 HTML 报告对比交易清单，扩展为正式基准）：

- [ ] **golden trace 语料库**：开发期人工在 MT4 测试器跑语料库 EA（demo 终端，开发机离线操作，不违反"平台不用 MT 终端"约束），导出 HTML 报告入 `testdata/golden/`
- [ ] **对拍指标**两级：交易级（交易序列匹配率：方向+开平仓 bar±1）与结果级（净利润偏差 %）
- [ ] **北极星**：bar 收盘信号型 EA 交易级匹配 100%（可达成——此类 EA 不依赖 bar 内路径）；bar 内敏感型 EA 结果级偏差公示，不承诺一致
- [ ] **执行模型差异明示**：回测报告标注"本平台为 bar 级建模（对应 MT4 open prices 模式）"，对含追踪止损/窄止损的 EA 主动提示建模差异——参考 MT4 自己也公示 modeling quality 的做法，诚实是信任的来源
- [ ] **收敛路径（数据驱动，不预先承诺）**：若对拍基准显示 bar 内路径差异是主要失真源且阻塞真实用户 → 实现 M1 插值 tick 模型（MT4 同款算法，公开已知）；在此之前不做——先测量，后投入

### 12.5 bar vs tick：结构性裁决（接口按 tick 定型，保真度按阶梯投入）

> **架构决定级别**：本节包含回测引擎核心架构变更（事件驱动内循环 + L1/L2/L3 保真度阶梯），超出"MQL EA 兼容性"范畴。建议拆为独立 ADR（待创建），本文档引用其结论。

**决定性论据不是回测精度，是回测/实盘一致性的结构可能性。** LiveRunner 消费 mtapi `OnQuote` 实时流（push-first），实盘天然是事件驱动；若回测接口按 bar 定型，同一策略在两侧跑两套语义，“回测/实盘信号一致性”（整改计划 0.3a 的核心目标）在结构上不可测。MQL EA 本身也是 `OnTick` 语义，VM 把 `start()` 映射到 OnBar 是在错误层级做的语义窄化。

**结构承诺（一次定死，不再变）**：引擎内循环消费**价格事件流**（`PriceEvent`：tick 或 bar 收盘均为事件）；SimBroker 成交/SL/TP/挂单判定全部改为事件驱动；`sdk` 策略回调保留 `OnBar`（由 bar 收盘事件触发）并预留 `OnTick`。回测与实盘共用同一事件接口，区别仅在事件源保真度。

**保真度阶梯（数据驱动逐级投入，接口不变）**：

- **L1 bar 收盘事件**（现状等价，重构后的默认模式）
- **L2 OHLC 四点合成路径**：每 bar 展开为确定性悲观路径（阳线 O→L→H→C，阴线 O→H→L→C），解决 SL/TP 同 bar 歧义与挂单成交时序，零额外数据——**性价比最高的一级，随接口重构一并实现**
- **L3 M1 插值 every-tick**（MT4 同款算法）：仅当 §12.4 对拍基准证明 L2 仍是主要失真源时投入

**硬依赖（排序约束）**：事件接口重构必须**先于整改计划 0.3a 的补测**——否则 70% 覆盖率的测试写在 bar 形接口上，接口一改全废。重构本身量级为天（Engine 内循环 + SimBroker 判定函数），并入 Phase 0 与 0.3a 串行：先重构接口 → 再补测。

**摸底后的事实校准（2026-08-04 实测）**：

1. **与 ADR-0012（tick 不落盘）无冲突，无需推翻**。ADR-0012 取消的是 tick **持久化**（md_ticks 月增 125GB 不可持续），不是 tick **执行模型**。本裁决的阶梯零 tick 存储：L2 从现有 bar 展开合成路径（零额外数据）；L3 从 md_bars 的 M1 周期插值（bar 本就持久化，`period` 列已支持多周期）。MT4 测试器自己也是这么做的——every-tick 模式的 tick 是 M1 插值合成的，不是真实 tick 存储。
2. **REUSE: `sdk.TickStrategy` + `Runner.OnTick` 已存在**（`strategy/runner/runner.go:93-106`）——实盘侧的 tick 形接口已成型，结构缺口**只在回测引擎内循环**（bar 形）。重构范围比预估更小：对齐回测引擎到已有接口，不是发明新接口。
3. 回测引擎当前用 bar 收盘价+点差合成 tick（ADR-0012 审计确认 `engine.go:150`），即 L1 事实上已是"合成事件"思路，L2 是其自然延伸。

### 12.6 资金路径摸底（回应"是否需要全面摸底"）

**裁决：要摸底，但是有边界的资金路径审计，不是全项目通读。** 依据：本次连续在资金路径上发现 4 个未知 bug（常量静默 push 0、OrderType 映射、同 bar SL/TP 歧义、缺口成交），证明该区域存在系统性未审状态；但全库 154K 行通读既不可行也无必要（非资金路径的 bug 不会静默赔钱）。

**范围（与整改计划 0.3a 完全重叠，审计即补测，不另起工作流）**：

| 模块 | 审计方式 | 产出 |
|------|---------|------|
| `tools/mql2go` VM 内置函数（交易类 ~40 个） | 逐个对照 MQL 文档验返回值/副作用，写单测固化 | 测试 + 发现的 bug 进批次 1 类清单 |
| `strategy/backtest`（Engine + SimBroker） | 事件接口重构时逐函数过审，补测到 70% | 同 0.3a |
| `strategy/runner` + `oms` | 0.3a 既定范围 | 同 0.3a |
| 指标库 `strategy/indicators` | 不逐行审，用 §12.1 D3 差分对拍兼测 | nightly CI |

审计中发现的每个 bug 入失败签名库（§12.1 Layer 2），修复必带回归测试。非资金路径模块维持整改计划附录 A 的"系统可验证性"策略，不扩大摸底范围。

### 12.7 与整改主计划的关系

批次 1、2 并入 **Phase 0**（用户 EA 跑不出正确结果 = 内测门槛"生成→回测闭环"直接失败，优先级等同稳定性底线）；批次 3 与 **Phase 0.5 内测**并行——内测种子用户的真实 EA 正是语料库冷启动的最佳来源。北极星指标（EA 首次回测成功率）纳入 Phase 0.5 验证门槛的观测项。
