## 0. 商业模型（本方案的收入假设）

| 收入线 | 定位 | 机制 | 时点 |
|--------|------|------|------|
| **订阅分层（主线）** | 真正的收入模型 | 按能力付费：高级模型、更高配额、实盘挂载数、回测并发。定价 $50–200/月，少量用户 × 高客单 | Phase 4 启用 |
| AI token 差价 | **成本回收机制，非卖点**（上游降价 + BYO 夹击，差价空间会被压缩） | 平台 key 通道按 token 计费，售价 = 成本 × 1.5–2.5x 分档 | Phase 2 上线 |
| BYO Key 免费 | 引流 + 信任门槛 | 用户自带 API key，平台不赚差价 | 已有 `agent_user_settings` 基础 |
| USDT 收款 | 支付通道 | `hdwallet`/`sweep`/`coldsign` 全链路**冻结不删**，后置启用 | Phase 4 |

**核心资产（长期）**：用户使用量沉淀的「策略生成 → 回测反馈 → 修改 → 实盘表现」全链路数据。这是数据飞轮，竞品无法复制。

## Phase 1 — 免费公测（Phase 0.5 验证通过后启动，持续 8–12 周）

目标：**换数据，不换钱。** 验证「描述 → AI 生成 → 免终端回测 → 挂实盘」闭环的留存，同时喂数据飞轮。

### 1.1 配额与成本控制（P0，公测前提）
免费 ≠ 无限。平台 key 的 token 成本是公测期最大现金支出：
- [ ] 每用户每日 AI 调用配额：免费档 **5 次生成会话/日 + 200K token/日**（`admin_config` 可调），超限提示次日恢复或切 BYO key
- [ ] token 用量计量：**REUSE 现有 `ai_token_usage` 表（migration 015）+ `AITokenUsageRepository`，仅加 `session_id` 列**，不新建表 — **这张表同时是 Phase 2 计费和数据飞轮的地基**
- [ ] 后端在 agent gateway 层统一记账（LLM 响应的 usage 字段），`decimal` 计价，禁止 float
- [ ] 全平台日成本熔断阈值：起步 **$50/日**（`admin_config` 可调），超阈自动降级到 BYO-only + 告警，防止被刷

### 1.2 AI 策略生成多语言适配（分两档）
现有语言：`en` / `zh-cn` / `zh-tw` / `ja` / `vi`（`frontend/src/i18n/resources/`）。
**负责人决策：P0 只做 zh-cn + en（验证闭环优先）；`zh-tw`/`ja`/`vi` 降为 P1，公测第 4 周后若非中英 locale 访问占比 ≥ 15% 再启动**。架构上一次做对（输出语言指令参数化），扩语言只是加测试。
- [ ] Agent 系统提示词（`internal/agent/prompts/`）接受用户语言参数：**内部推理/工具调用固定英文，仅面向用户的输出文本按 locale 生成**（系统提示词加输出语言指令，非整体切换）；MQL 代码及其内部注释统一英文，locale 化说明放代码块外
- [ ] AI 输出的解释性文本（策略说明、参数说明、回测解读）按 locale 生成，不走事后翻译；另为 `ja`/`vi`/`zh` 非 ASCII 注释源码各加 1 条编译回归测试（防用户粘贴代码）
- [ ] 澄清问答（`internal/ai/clarification`）架构参数化支持 5 语言，P0 实现 zh-cn + en，其余随语言启用补充
- [ ] 每个已启用语言至少 3 条端到端验收用例（描述→生成→回测通过），进 Playwright E2E（复用 `playwright-backtest` 模式）
- [ ] 错误消息 / blind-spot 警告走现有 proto i18n 管线（textproto → `i18n-build.ts`）

### 1.3 公测运营配套（P1）
- [ ] 注册开放 + 邮箱验证（已有 `verifyemail`），暂不设邀请码——小众市场没有刷量价值
- [ ] 站内反馈入口（每次生成会话可一键「好/差 + 原因」）——这是飞轮的显式标注信号
- [ ] 关键漏斗埋点（已有 umami）：注册 → 首次生成 → 首次回测 → 首次绑定 MT 账户 → 首次实盘
- [ ] 状态页（可用 uptime-kuma 单容器），mtapi 熔断状态同步展示

### 1.4 公测期不做的事（明确排除）
- ❌ 策略市场运营（保留展示，不投入开发）
- ❌ 新指标/新功能大类
- ❌ USDT 通道启用

## Phase 2 — AI Token 差价计费（公测第 4–6 周并行开发，公测结束前上线）

目标：公测结束时无缝切换「免费额度 + 付费额度」，差价收入覆盖 AI 成本并产生毛利。

### 2.1 计费模型
- 计价单位：**平台积分（credits）**，**1 credit = $0.01**（DB 存 `NUMERIC(20,8)`，展示取整）。用户视角只看 credits，屏蔽各厂商价差
- 与订阅关系（Phase 4）：**订阅档位每月赠送 credits 额度**（记为 `subscription_grant` 类型交易，当月有效），超额消耗从充值余额扣；`credit_accounts` 不加订阅外键，赠送来源记在 `credit_transactions.source`
- 售价 = 厂商成本 × 加价系数，按模型分档（旗舰模型 1.5x，轻量模型 2.5x——轻量模型毛利率高且够用）
- BYO key 用户：0 差价，但不享受平台模型白名单外的托管模型
- 免费档保留（每日小额度）：持续获客 + 飞轮数据不中断

### 2.2 实现清单
- [ ] `ai_token_usage`（Phase 1 已扩展）之上加 `credit_accounts` + `credit_transactions`（复用现有钱包表结构思路，`NUMERIC(20,8)`）
- [ ] 预扣-结算模式：会话开始**固定预扣**（该模型单轮会话 P90 历史成本，冷启动用人工估的保守值），每轮工具调用后增量结算，会话结束多退少补（防止长会话透支）
- [ ] 余额不足 → 会话中断前警告 → 优雅收尾（保存已生成内容）
- [ ] 管理后台：模型成本价/售价配置（复用 `admin_config` / `ManagedConfig.AllowedModels` 机制）
- [ ] 充值方式（合规后置前提下的过渡）：**先只做后台人工充值**（admin 手动加 credits，用户线下付款）——工作量最小，验证付费意愿；USDT 自动充值留给 Phase 4
- [ ] 退款政策随充值上线同步声明：**未消费充值 credits 7 日内可人工退款（原路退回），已消费不退，赠送/免费额度不可退**，写入充值页条款

### 2.3 验收
- [ ] 计费对账：`ledger` 汇总 = 厂商账单 ±1%（每周人工核对一次）
- [ ] 计费路径测试覆盖 ≥ 70%（0.3b 归属，并入分模块闸门）

## Phase 3 — 数据飞轮（贯穿公测，收获在 3–6 个月后）

原则：**现在只做「采集正确」，不做训练。** 数据 schema 错了后期无法补救；训练/微调等量到了再说。

### 3.1 采集 schema（P0，公测开始前定稿）
存储策略：**轨迹事件用 `AgentTrajectoryEvent` proto（oneof）序列化存 `BYTEA`；可查询聚合指标（成功率/token 数/locale）拆关系列同表存**，不用 JSONB。每次生成会话记录：
- 用户输入（原始描述 + locale + 澄清问答链）
- Agent 全轨迹（工具调用序列、生成的 MQL、修改 diff 链）
- 回测结果指标（收益/回撤/交易数/胜率——已有回测报告结构）
- 用户显式反馈（好/差 + 原因，来自 1.3）
- 隐式信号：是否保存、是否二次修改、是否挂实盘、实盘存活天数
- [ ] 匿名化边界：账户凭据、余额绝不入采集表

### 3.2 数据利用路线（按量分级触发）
| 数据量 | 动作 |
|--------|------|
| ~500 会话 | 失败模式人工归类 → 改 prompt / 补 `builtin_registry` 盲点，立即提升生成质量 |
| ~5K 会话 | 高分策略模板库（few-shot 检索注入 prompt）——RAG 不是微调，成本低见效快 |
| ~50K 会话 | 评估集固化 + 考虑小模型微调（仅当 RAG 天花板显现） |

### 3.3 护城河声明
飞轮的壁垒不在模型，在**「生成 → 回测 → 实盘表现」的闭环标注数据**——只有同时握有执行链路的平台才采得到。这是对外融资/合作叙事的核心资产，采集质量优先级高于一切模型工程。

## 附录 A — AI 生成代码库的人类治理策略

背景：全库 ~154K 行非测试 Go 代码基本由 AI 辅助生成，单人无法逐行理解。
**目标不是"让人读懂全部"，而是把「人的理解」换成「系统的可验证性」**——在不完全理解实现的情况下也能安全地修改与运维。分五层执行：

### A.1 测试即规格（最重要）

测试是人类与 AI 代码之间的合同：

- Phase 0.3 的分档核心模块 70% 覆盖率（0.3a 先行，0.3b 随 Phase 2/4）即为此服务
- **执行红线：测试用例本身必须由人工逐条 review。** AI 写实现可以，AI 自己写测试验证自己 = 没有验证
- 赔钱路径（计费、归集、回测盈亏）用表格驱动测试 + **人工手算的期望值**——人算的数字就是人类锚点

### A.2 契约边界人审，实现层放权

- 142 个 proto 文件是人类可读的系统地图：**人只审 proto（接口/字段/语义），实现层交给 AI + 测试守护**
- 数据库 migrations 同理。业务 proto（7,840 行）+ migrations 全量（7,220 行，大半为历史增量）合计 ≈1.5 万行，人力可覆盖

### A.3 不变量自动化（已有机制，坚持执行）

`check-file-lines`、禁止 float64/JSON/REST/WebSocket、`cap.sh` 复用核对、CI 覆盖率闸门——AI 代码库的质量靠**机器执法**而非人工 code review。任何新不变量优先做成 CI 检查而不是文档约定。

### A.4 深度理解只投给 20%

按风险分级人的理解投入：

| 级别 | 范围 | 要求 |
|------|------|------|
| 逐行理解 | 资金路径（credits 账本、sweep 归集、计费预扣结算）、VM 安全机制（指令计数/panic recovery） | ~1–2 万行，人力可及，必须掌握 |
| 接口级理解 | mthub、mdgateway、marketplace | 读 proto + 模块 README 即可 |
| 黑盒 + E2E 兜底 | 前端页面、i18n、admin | Playwright 回归保护 |

### A.5 用 AI 对抗 AI：定期审计代替阅读

- 每月让 AI 对指定模块出审计报告：「实现与测试是否一致、有无静默行为变更、有无违反不变量」，人只读报告
- 配合运行时验证代替静态阅读：Prometheus 告警、计费对账 ±1%（2.3）、solvency-check 日检（Phase 4）

**一句话总结**：人的角色从"读代码"转为"审合同"——合同 = proto + schema + 测试期望值 + 不变量规则，这四样人力完全可覆盖；实现层正确性交给测试、CI 执法和运行时对账。
