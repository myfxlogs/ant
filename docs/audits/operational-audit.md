# 营运视角全站审计

> 站在营运决策角度看 11 个功能块。审的不是技术，是"该不该"。

---

## 1. 收入模型回顾

平台只有三条收入线：

| 收入线 | 状态 | 依赖 |
|--------|------|------|
| 平台订阅（Free/Pro/Enterprise） | ⏳ 策略市场完工后启用 | strategy-marketplace |
| 策略抽成（15-30%） | ⏳ 同上 | strategy-marketplace |
| AI token | ✅ 已上线 | agent-engine |

当前实际收入：**AI token 超额部分**。平台订阅和策略抽成尚未启动。

## 2. 逐块营运判断

### mt-gateway — 🟢 必须运行

**营运判断**：不能关。关了就断开了所有 broker 连接。不是收入问题——是整个平台的存在性问题。

**成本**：mtapi.io 代理（外部服务，按连接数计费）+ 服务器带宽。无调整空间。

### market-data — 🟢 必须运行

**营运判断**：不能关。行情数据是所有策略的基础。但可以降本——ClickHouse 的存储成本高于 PG，如果策略数量少，可以暂时只用 PG 存 K 线，CH 留到量起来后再启用。

**优化空间**：🟡 低策略量时关 CH，全存 PG。

### mql-compiler — 🟢 必须运行

**营运判断**：不能关。没有编译器就没有策略。成本是 CPU（编译时），非持续消耗。

### strategy-runtime — 🟢 必须运行

**营运判断**：不能关。策略执行引擎。

### backtest-engine — 🟢 必须运行

**营运判断**：不能关。回测 = 质量门槛。但可以限制并发回测数来控制 CPU 成本。

### risk-gate — 🟢 必须运行

**营运判断**：不能关。没有它实盘策略无安全网。

### account-mgmt — 🟢 必须运行

**营运判断**：不能关。用户系统 + 钱包。但钱包的 TronGrid/TronScan API 调用是按量计费的——如果存入频次低，成本可忽略。

### api-gateway — 🟢 必须运行

**营运判断**：不能关。通信基础设施。

### frontend — 🟢 必须运行

**营运判断**：不能关。但有优化空间——Landing Page 是纯静态的，可以 CDN 缓存。策略市场页面同理。

### agent-engine — 🔴 需要降本或推迟

**营运判断**：当前最大的成本中心。每个策略生成调用消耗 LLM API token（OpenAI/Anthropic）。Phase 2 的"AI 批量生成 200+ 策略"= 大批量 token 消耗。**在策略市场没有产生收入之前，AI 批量生成应该冻结。**

**当前 agent-engine 应该保留的功能**：
- ✅ 提供者在工作区手动调 AI 生成策略（单个、按需，token 成本可计费回收）
- ✅ AI 策略迭代更新（Phase 5，策略已经上线后自动优化）——这是收入驱动而非成本驱动

**当前 agent-engine 应该冻结的功能**：
- ❌ 批量自动生成策略入库（Phase 2.2）——纯烧钱，无收入
- ❌ 平台侧主动扫描品种×周期生成策略——同上

### strategy-marketplace — 🟡 优先推进

**营运判断**：唯一能产生**新收入**的块。不是技术优先级——是生存优先级。Phase 1-2 完工 → 策略市场上线 → 平台订阅 + 策略抽成启动 → 覆盖运营成本。

---

## 3. 成本结构评估

| 成本项 | 月估 | 可降本？ |
|--------|------|---------|
| LLM API token（agent-engine） | 最高 | ✅ 冻结批量生成，只留按需 |
| mtapi.io 连接 | 低 | ❌ 固定成本 |
| TronGrid/TronScan API | 低 | ❌ 按调用量，存入少则低 |
| ClickHouse | 低 | 🟡 低量时关 |
| PG / Redis / NATS | 低 | ❌ 固定成本 |
| 服务器 | 中 | ❌ 固定成本 |

**结论**：唯一可以显著降本的是 LLM API token。冻结 agent-engine 的批量生成，月成本可大幅降低。其他成本都是固定的。

---

## 4. 营运优先级重排

```
P-1（生存级）: 冻结 agent-engine 批量生成 → 降本
P0（收入级）: strategy-marketplace Phase 1-2 → 产生收入
P1（产品级）: strategy-marketplace Phase 3-4 → 增长
P2（效率级）: agent-engine 按需生成 + AI 迭代更新（Phase 5）
P3（降本级）: ClickHouse 降级、frontend CDN 优化
```

---

## 5. 结论

**技术上 11 个块全完整，营运上只需跑 10 个。** agent-engine 不是不用——是不该批量用。保留按需生成（用户付 token 费），冻结批量灌库（平台烧钱）。GLM 完工后，`batchGenerator.Start()` 暂不接入，等收入跑正后再开。

**一句话**：先让市场跑起来、产生收入，再用收入养 AI。
