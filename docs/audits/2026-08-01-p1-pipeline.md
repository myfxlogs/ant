# P1 行情引入管线逐行审计 — 2026-08-01

## 数据流

```
MT4/MT5 tick stream
    │
    ▼
Manager.HandleTick (6-stage pipeline)
    │
    ├── 1. normalize: raw symbol → canonical (PG lookup + cache)
    ├── 2. quality:   bid>ask, non-positive, clock skew → hard drop
    │                 outlier detection (median+MAD) → tag only, never drop
    ├── 3. stuffing:  quote rate > threshold → drop
    ├── 4. dedup:     ring buffer hash → skip duplicates
    ├── 5. aggregate: tick → bar (OHLC, 8 periods 1m→1w)
    ├── 6. publish:   NATS tick + bars, onBar callback, Redis latest quote
    └── 7. enqueue:   PG batch insert bars
```

## 逐环节审查

### 1. Normalizer (normalizer.go)

✅ Double-checked locking: RLock → check → RUnlock → Lock → recheck → PG query。
✅ 3s PG 查询超时。
✅ 无算法后缀剥离——正确避免 broker 不匹配。

| 行 | 严重度 | 问题 |
|----|--------|------|
| 44-47 | 🟡 MEDIUM | 缓存满 100k 时**全量 reset**——所有条目一次性丢失，引发 PG 查询雪崩（thundering herd）。应改为 LRU 淘汰或分段过期 |

### 2. Quality (quality.go)

✅ Hard drop 正确: bid>ask、非正价格、时钟偏差>5s。
✅ 异常检测: median + MAD，仅标记不丢弃——遵循 LMAX/Bloomberg 理念。
✅ 价差 Z-score 追踪 + 异常计数。

| 行 | 严重度 | 问题 |
|----|--------|------|
| 98-99 | 🔵 LOW | `bidF, _ := t.Bid.Float64()` ——decimal→float64 精度损失。统计路径可接受，但丢失的精度意味着异常值判断在~1e-15 级别可能偏差 |
| 107-125 | 🔵 LOW | `q.mu.Lock()` 覆盖异常检测+gap 记录——热点路径上锁范围可缩小 |

### 3. Dedup (tick_dedup.go)

✅ 环形缓冲区 + hash set: O(1) 查找。
✅ ArrivedUnixMs 排除——live 与 replay 生成相同 hash。
✅ 窗口大小 1000，覆盖 broker 重连重放场景。

无问题发现。

### 4. Bar Aggregator (bar_aggregator.go)

✅ 8 周期: 1m/5m/15m/30m/1h/4h/1d/1w。
✅ 中间价: `(bid+ask)/2` 用于 OHLC——正确。
✅ Bar 完成检测: bucket 变更时输出完成 bar。
✅ finalizedBars 去重: 防止外部 bar（backfill）重复。

| 行 | 严重度 | 问题 |
|----|--------|------|
| 114 | 🔴 HIGH | `ob.volume += float64(t.BidVolume + t.AskVolume)` ——**Volume 用 float64 累加**。大成交量账户（>1e15）累积误差可达 1-2 单位。应改为 `decimal.Decimal` 累加 |
| 27 | 🟡 MEDIUM | `openBar.volume` 字段类型为 float64——与上一行同一问题，需要整个字段改为 decimal |
| 85-106 | 🔵 LOW | Bar 重置时字段赋值重复（init + reset 两处相同的 10 个字段赋值）——维护风险：加新字段需改两处 |

### 5. PG Writer (pg_writer.go)

✅ 批处理: 2000 bar/batch。
✅ 非阻塞入队: channel + default 分支，满时丢弃 + 计数。
✅ 3 次重试 + 指数退避: 200ms → 400ms → 800ms。
✅ 优雅关闭: ctx.Done 时 Flush 剩余 bar。

| 行 | 严重度 | 问题 |
|----|--------|------|
| 61 | 🔵 LOW | `AllowCHWrite(b.UserID, 512)` ——函数名 `AllowCHWrite` 引用已删除的 ClickHouse，应重命名 |

### 6. Manager HandleTick (manager_tick.go)

✅ 6 阶段管线清晰。
✅ Stuffing 检测: pause 检查 + Observe，drop 时静默跳过。
✅ Redis 最新报价缓存: 1h TTL。
✅ onBar 回调: 驱动实时策略执行（P2 管线连接点）。

| 行 | 严重度 | 问题 |
|----|--------|------|
| 22-94 | 🟡 MEDIUM | 每 tick 6 个 OTel span——无采样。热点路径上持续分配 span 对象（审计 A-021） |

## 各环节评级

| 环节 | 评级 | 评语 |
|------|------|------|
| Normalizer | 🟢 良 | Double-checked locking 正确，缓存 reset 需改进 |
| Quality | 🟢 良 | 硬丢弃规则正确，异常检测不丢弃 |
| Dedup | 🟢 良 | Ring buffer + hash，设计正确 |
| Bar Aggregator | 🟡 中 | 逻辑正确，Volume float64 是唯一的精度问题 |
| PG Writer | 🟢 良 | 批处理+重试+优雅关闭 |
| Manager | 🟢 良 | 6 阶段结构清晰，span 开销需优化 |

**总评**: P1 管线整体设计优秀——6 阶段管线结构清晰，去重/质量/归一化逻辑正确。唯一的精度缺陷是 bar Volume 的 float64 累加——对零售账户无影响，但对高成交量机构账户可能产生可见的 bar volume 偏差。`bar_aggregator.go` 是唯一需要修改的文件。
