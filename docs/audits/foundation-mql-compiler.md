# 地基审计 · mql-compiler

## 1. 核心设计替代方案

**当前**：MQL/Python → tree-sitter → IR → Bytecode → VM。确定性管道。277+ 内置函数。

**替代方案 A**：解释执行 MQL AST（不编译到字节码）。

不选。解释执行每遇到一个函数调用就要查表、匹配、执行。字节码 VM 是一次编译、重复执行。性能不在一个量级。选择编译是正确的。

**替代方案 B**：直接用 Go 写策略，不做 MQL 兼容。

不选。MQL 生态是全球最大零售算法代码库。兼容 MQL = 供给侧竞争力（桥接数万已有 EA 的开发者）。放弃 MQL = 放弃最大的供给侧市场。

**替代方案 C**：LLM 直接生成 Go 字节码，跳过 MQL 编译。

不选。LLM 生成的字节码不可验证、不可回测、不可调试。确定性管道是"回测=实盘"的保证。跳过编译 = 放弃这个保证。

**结论**：✅ 编译管线是最优解。当前唯一的架构问题是 MQL 有限集——~40% 真实 EA 因盲区无法运行。这是已知取舍，盲区桥接（agent-engine）是缓解手段。

## 2. 上下游契约

**上游**：agent-engine 提交源码 → tree-sitter 解析 → 编译。

**下游**：strategy-runtime 和 backtest-engine 加载字节码 → VM 执行。

**隐患**：IR 层是 MQL 语义的超集还是 MQL 的子集？如果是子集，新 MQL 特性加入时需要改 IR——所有下游都要重新适配。需要确认 IR 的设计意图。

**另一个隐患**：builtins.go 注册的 277 个函数——是手动维护的列表还是从 tree-sitter 语法树自动生成的？手动维护意味着 MT 新增函数时需要手工同步，漏掉就会变成盲区。

## 3. 已知架构债务

| 债务 | 严重度 | 方案 |
|------|--------|------|
| ~40% 真实 EA 因盲区无法运行 | 🟡 | 已知取舍。盲区桥接（agent-engine）是缓解，不是解决。长期需评估 IR 扩展成本 |
| builtins 手动维护 | 🟡 | 确认是否可以部分自动化（从 proto 定义推导内置函数列表） |
| 平台依赖 MetaQuotes（R-P） | 🔴 | MQL 语法/语义归其单方控制。IR 层是去耦合的关键——确认 IR 是否可接入非 MQL 前端 |

## 4. 总评

编译管线是最优解。平台依赖（R-P）是长期最大风险——IR 层的独立性决定了被 MetaQuotes 锁定的程度。两个黄标需要验证后决定要不要改。一个红标（R-P）是战略风险，不在代码层面解决。
