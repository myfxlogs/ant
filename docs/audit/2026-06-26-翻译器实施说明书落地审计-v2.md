## 3. Layer 2/3 迁移引擎 — 架构审计

> **新增**：v1 完全未审计 `tools/mql_migration/`（22 个文件）。以下为 v2 补充。

### A1 — IR 语言绑定：`Condition` / `OrderParams` 双重表示，声称语言无关实则 Python 耦合

**严重度**：P1 — 架构设计缺陷

`intent_ir.py:124-153` — `Condition` 同时持有 `ast_node`（语言无关）和 `expr`（Python 缓存字符串）。`OrderParams` 同时持有 `volume`/`volume_ast`、`price`/`price_ast`、`sl`/`sl_ast`、`tp`/`tp_ast`。

IR 文档注释声称"语言无关"，但 `expr` 字段在识别器阶段就被 `ExpressionGen.translate()` 填充为 Python 字符串。代码生成器 `python_gen.py:267-270` 优先使用 `ast_node`，但 `_build_condition()` (`:378-381`) 直接用 `c.expr`，不走 AST 翻译。

**后果**：
- 如果未来要支持 Go/其他目标语言，`expr` 缓存全部不可用
- 识别器在识别阶段就调用了 `ExpressionGen`，把"理解意图"和"生成代码"两个阶段耦合了
- `ast_node` 和 `expr` 可能不一致——识别器翻译时的 `ExpressionGen` 状态（`_local_vars`、`_inside_orderselect_loop`）与生成器翻译时的状态不同

**要求**：二选一：
1. 如果 IR 真的要语言无关：删除所有 `expr`/`volume`/`price`/`sl`/`tp` 缓存字段，只保留 `ast_node`/`volume_ast` 等，代码生成器统一翻译
2. 如果当前只用 Python：删除 `ast_node` 字段，IR 明确标注为 Python-bound，停止声称语言无关

### A2 — `ExpressionGen` 状态共享：识别器手动 save/restore，有 `local_scope` 却不用

**严重度**：P1 — 状态管理不一致

`ExpressionGen` 有可变状态 `_local_vars: Set[str]`，影响标识符翻译结果（`_map_ident` 判断是 `self.xxx` 还是裸名）。

`expression_gen.py:94-120` 提供了 `_LocalScope` 上下文管理器（`local_scope()`），自动 save/restore。

但**所有 6 个识别器**都用手动 save/restore 模式，没有用 `local_scope()`：

```python
# market_entry.py:69-75 (重复出现在 pending_entry, custom_entry, magic_exit, margin_check, pipeline._recognize_risk)
prev_locals = set(expr_gen._local_vars)
expr_gen._local_vars |= local_vars
# ... work ...
expr_gen._local_vars = prev_locals
```

**风险**：
- 如果识别器中间 `return` 或抛异常，`prev_locals` 不会被恢复（`custom_entry.py:83` 就有 early return）
- `pipeline.py:304-307` 的 `_recognize_risk` 甚至直接操作 `self._expr_gen._local_vars`，跨越了模块边界

**要求**：所有识别器统一改为 `with expr_gen.local_scope(local_vars):`，删除手动 save/restore。

### A3 — 识别器 AST 遍历逻辑重复

**严重度**：P2 — 代码重复

`base.py` 有三个 AST 遍历函数，逻辑高度重叠但实现不一致：

| 函数 | 处理的节点类型 | 用途 |
|------|---------------|------|
| `find_calls()` (`:72-106`) | CompoundStmt, IfStmt, ForStmt, ExpressionStmt, BinaryOp, UnaryOp, VarDecl, AssignmentExpr | 收集 CallExpr |
| `ast_contains_call()` (`:210-241`) | 同上 | 布尔判断是否包含 |
| `custom_entry.py:150-180` `_ast_var_refs()` | Identifier, CallExpr, BinaryOp, UnaryOp, IfStmt, CompoundStmt, ExpressionStmt | 收集变量引用 |

`_ast_var_refs()` 是 `custom_entry.py` 内部定义的，没有复用 `base.py` 的遍历基础设施。如果 `base.py` 的 `find_calls` 漏了某个节点类型（比如 `TernaryExpr`），三个函数的行为会不一致。

**要求**：抽取统一的 `ast_walk(node, visitor_fn)` 泛型遍历器，`find_calls`/`ast_contains_call`/`_ast_var_refs` 都基于它实现。

### A4 — `_str_to_order_action` 在三个识别器中重复定义

**严重度**：P2 — 代码重复

同一个 dict `{("market_buy", OrderAction.MARKET_BUY), ...}` 出现在：
- `market_entry.py:38-48` — `_order_action_from_str()`
- `pending_entry.py:42-51` — `_str_to_order_action()`
- `custom_entry.py:44-53` — `_str_to_order_action()`

三份代码完全相同，只是默认值不同（`MARKET_BUY` / `BUY_LIMIT` / `BUY_STOP`）。

**要求**：移到 `base.py`，接受 `default` 参数。

### A5 — `python_gen.py` 指标参数推断用关键词匹配，不可靠

**严重度**：P2 — 逻辑脆弱

`python_gen.py:220-227` `_find_param_for()` 用关键词子串匹配从 `intent.params` 推断指标参数：

```python
def _find_param_for(intent, keywords: list[str], default: int) -> str:
    for p in intent.params:
        lower = p.name.lower()
        if any(kw in lower for kw in keywords):
            return f"self.{p.name}"
    return str(default)
```

问题：
- `"period"` 匹配 `"MAPeriod"` 也匹配 `"RSIPeriod"`——如果策略同时有 MA 和 RSI，第一个匹配的 param 会被两个指标共用
- `"fast"` 匹配 `"FastMA"` 也匹配 `"FastExit"`——语义无关的参数可能被误绑定
- `IndicatorSpec` 已经有 `params: Dict[str, Any]`，但 `_indicator_code()` 完全没用它

**要求**：`IndicatorSpec.params` 在识别器阶段填充实际参数值（从 MQL `iMA(symbol, timeframe, period, ...)` 的 args 中提取），`python_gen` 直接使用，不做关键词猜测。

### A6 — `pipeline.py` 直接操作 `expr_gen._local_vars` 跨模块

**严重度**：P2 — 封装泄露

`pipeline.py:304-307`:

```python
prev = set(self._expr_gen._local_vars)
self._expr_gen._local_vars |= locals_
condition_expr = self._expr_gen.translate(cond)
self._expr_gen._local_vars = prev
```

Pipeline 直接读写 ExpressionGen 的私有状态 `_local_vars`，绕过了 `local_scope()` 上下文管理器。

**要求**：改为 `with self._expr_gen.local_scope(locals_):`。

### A7 — `python_gen.py:511-529` `_extract_refs()` 函数从未被调用

**严重度**：P2 — 死代码

`_extract_refs()` 是一个复杂的正则函数，但全文搜索没有任何调用方。可能是早期设计的残留。

**要求**：删除。

### A8 — `python_gen.py:553-555` 反向依赖 Layer 1

**严重度**：P2 — 层级耦合

```python
def _py_default(param: ParamSpec) -> str:
    from tools.mql_transpiler.ast_transpiler import ASTTranspiler
    return ASTTranspiler._mql_default_to_py(val, param.param_type.value)
```

Layer 3 代码生成器反向 import Layer 1 翻译器的内部方法。`_mql_default_to_py` 是一个静态方法，应该提取到共享工具模块或直接在 IR 中存储 Python 默认值。

**要求**：将 `_mql_default_to_py` 提取到 `tools/mql_migration/` 内部工具模块，或让识别器在 `ParamSpec.default` 中直接存储 Python 字面量。

### A9 — Registry 注册了 11 个识别器，Pipeline 一个都没用

**严重度**：P1 — 架构断裂

`registry.py:220-300` `RecognizerRegistry.create_default()` 注册了 11 个识别器：`market_entry`, `pending_entry`, `custom_entry`, `magic_exit`, `exec_model`, `sizing`, `params`, `state_vars`, `meta`, `timer`, `margin_check`。

但 `pipeline.py:92-202` `_analyze_ast()` **完全绕过 Registry**，直接硬编码调用 11 个识别器函数，自己管理调用顺序、参数处理（如 martingale params 注入、lot fallback）、覆盖率计算。

**后果**：
- Registry 的 `run_all()`、`AggregateResult`、盲区追踪、开发阈值触发——全部是死代码
- 新增识别器需要同时改 Registry 和 Pipeline，容易遗漏
- Registry 的异常隔离（`try/except` per recognizer）在 Pipeline 中不存在——一个识别器崩溃会阻断整个管线

**要求**：Pipeline 改为 `registry = RecognizerRegistry.create_default(); result = registry.run_all(ast, expr_gen)`，Pipeline 只负责从 `AggregateResult` 组装 `StrategyIntent`。识别器间的参数处理逻辑（martingale 注入、lot fallback）移到 Pipeline 的后处理步骤。

### A10 — 覆盖率虚高：`meta`/`execution`/`sizing` 永远 +1

**严重度**：P1 — 度量失真

`pipeline.py:114-130`:

```python
meta = recognize_meta(ast, source_name)
blocks["meta"] = 1          # 永远 = 1，不管 meta 是否有意义

execution = recognize_execution_model(ast)
blocks["execution"] = 1    # 永远 = 1，即使返回默认值

sizing = recognize_sizing(ast)
blocks["sizing"] = 1        # 永远 = 1，即使返回默认 SizingRule.FIXED
```

覆盖率计算 (`:178-185`)：`meta`(weight=1) + `execution`(weight=1) + `sizing`(weight=1) = 3 分永远到手。总权重 12，即 **25% 基线分是白送的**。

一个只有 `meta` + `execution` + `sizing` + `params` 被识别（entries/exits/indicators/risk/timer 全空）的策略，覆盖率 = 4/12 = 33%，看起来"还行"，实际什么交易逻辑都没识别到。

`test_e2e.py:84-87` 断言 `coverage_score >= 0.5`——这个阈值在有 25% 白送分的情况下太宽松。

**要求**：
1. `meta`/`execution`/`sizing` 的 `blocks` 值改为基于返回内容的实际判断（如 `meta` 有 name 才 =1，`sizing` 非 FIXED 默认才 =1）
2. 或者从覆盖率权重中移除结构性块（meta/params/state/execution/sizing），只计交易逻辑块（entries/exits/indicators/risk/timer）
3. 调整 `test_e2e.py` 阈值 accordingly

### A11 — import API 直连 Python REST+JSON，违反 CLAUDE.md 红线

**严重度**：P1 — 违反约束文档

`CLAUDE.md:39` 红线：❌ REST endpoints；`CLAUDE.md:41` 红线：❌ JSON 作为数据序列化/交换格式。

当前 import API 路径：前端 → Python REST endpoint（JSON body）→ 直接调用 Python ConnectRPC server。Python ConnectRPC server 用 protobuf 库，但编译的 pb2 用 `google.protobuf`，两个库不兼容——所有直连 Python 的 ConnectRPC 请求 codec 失败。

前端之所以能用其他端点，是因为走 Go 代理。import API 也应走 Go 代理。

**要求**：给 Go backend 加 ConnectRPC proxy 方法，前端→Go→Python 全链路 proto，删除 REST 端点。环境有 Go 1.22 可编译。

## 4. 可优化

### O1 — Lint 正则对 URL 中的 `//` 可能误报

`quality_gate.py:75`：`(?<!['\"])\/\/` 的 negative lookbehind 只排除紧邻引号的 `//`，但 `"http://example"` 中 `//` 前面是 `:`，不在排除范围。建议先 `ast.parse` 提取字符串字面量，只检查非字符串区域的 `//`。

### O2 — MQL5 grammar `.so` 未编译

`grammar/mql5/` 只有 2 个文件（无 `.so`），`tree_sitter_parser.py` 检查 `mql5.so` 不存在时静默回退到 MQL4 grammar。MQL5 EA（class/OOP 语法）会按 C 语法解析，可能产生错误 CST。应在日志中 warning，或编译 MQL5 grammar。

### O3 — `connectrpc_server.py:60` HIGH→1.0 / LOW→0.0 仍用 float 字段

API 返回 `confidence: float`，消费者可能误以为 0.5 是"中等置信"。建议 proto 字段改为 `string quality_verdict` 或至少在注释中标注 binary 语义。

### O4 — `gap_kb.py:110-114` 排除部分交易函数

`OrderSend`/`OrderClose` 等被排除在 unmapped scan 之外。建议移除排除列表，让 gap_kb 记录所有未映射符号。
