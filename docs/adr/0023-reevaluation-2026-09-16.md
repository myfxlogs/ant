- **日期**：2026-09-16
- **类型**：正式架构再评估（方案/设计审查）
- **触发**：业主要求对 VM 管线做全面重新评估，判断是否还有更优解
- **依据**：ADR-0023 原始决策 + 2026-09-16 深度审计报告（`docs/audits/vm-pipeline-deep-audit-2026-09-16.md`）+ 本次事实核验

## 0. 评审判定

**🟡 条件通过**——当前四段式架构（CST→IR→Bytecode→Stack VM）方向正确，**不需要推翻重写**；但存在明确的优化空间与语义边界风险，建议按优先级分阶段演进。

**不建议**：重写为寄存器 VM、嵌入外部 runtime（goja/starlark/yaegi）、回到 Go codegen/WASM、改为树遍历解释器——这些方案要么已被 ADR-0023 否决且理由仍然成立，要么引入新的失真层，要么收益不足以覆盖重写风险与重审计成本。

**建议**：保留架构 + 有针对性优化（方案 F），详见 §5。

## 2. 备选方案对比矩阵

| 方案 | 语义保真 | 性能 | 安全性 | 可维护性 | 可观测性 | 开发成本 | 综合 |
|------|----------|------|--------|----------|----------|----------|------|
| **A 现状（Stack VM）** | 9 | 7 | 9 | 7 | 9 | — | **8.2** |
| B 寄存器 VM | 9 | 8 | 9 | 6 | 9 | 高 | 8.0 |
| C 树遍历解释器 | 8 | 4 | 8 | 8 | 7 | 中 | 6.4 |
| D 嵌入 runtime（goja/starlark/yaegi） | 5 | 7 | 6 | 7 | 5 | 高 | 6.0 |
| E AOT 编译到 Go | 6 | 9 | 5 | 5 | 5 | 极高 | 5.4 |
| **F 现状优化（不调架构）** | 9 | 8.5 | 9 | 7 | 9 | 低 | **8.5** |

### 2.1 方案 B：寄存器 VM

**理论收益**：Lua 从 stack 迁移到 register 获得 ~2x 提升（减少 push/pop 指令数、常量池直接访问）。

**实际收益有限的原因**：
1. MQL 策略是 **builtin 调用密集**而非纯计算密集——大量时间在 `iMA/OrderSend/AccountBalance` 等 builtin 内，而非指令 dispatch。register VM 主要优化 dispatch + 栈操作，对 builtin 内部零收益。
2. VM 时间分布估算：dispatch 30-50% + 栈操作 20-30% + builtin 调用 30-50% + decimal 运算 10-20%。register VM 最多优化前两项合计 ~50%，理论上限 ~1.3-1.5x，而非 Lua 的 2x。
3. 重写成本：编译器后端 + VM 核心 + 所有不变量重新验证 + 重新审计，风险远高于收益。

**结论**：**不建议**重写。若未来性能瓶颈明确且优化空间耗尽，可作为长期演进选项，但需充分成本收益论证。

### 2.2 方案 C：树遍历解释器

**否决理由**：
1. 性能差 3-10x（每个 AST 节点递归调度，无法做跳转优化）。
2. 失去 Bytecode 的核心价值：
   - 编译期优化（常量折叠、跳转回填）
   - 执行状态可序列化（`MarshalBytecode` 缓存）
   - 指令级覆盖度报告
   - 指令级 fail-closed 语义（`fatalError`）
   - `SourceHash` 绑定缓存完整性
3. 回测吞吐不可接受（10K bars × 每 bar 数百节点递归）。

**结论**：**否决**。Bytecode 层不是冗余，是核心资产。

### 2.3 方案 D：嵌入外部 runtime

**否决理由**：
1. **语义失真**：MQL 不是 JS/Python/Go。嵌入 goja/starlark 需要 MQL→JS/Python 源到源翻译，引入新的失真层——正是 ADR-0023 否决 Go codegen 的同一问题。
2. **decimal 精度**：外部 runtime 用 float64，需自定义扩展注入 decimal——反而更难控制。
3. **series 语义**：MQL 的 `Close[0]` 反向索引、timeseries 数组、`ArraySetAsSeries` 在外部 runtime 中需大量自定义扩展。
4. **沙箱边界**：自研 VM 的 SDK 唯一出口比外部 runtime 的 FFI 边界更易精确控制与审计。
5. **现有投资作废**：tree-sitter parser、IR、覆盖率报告、Defense A、盲区机制、fail-closed 全链路都需重建。

**结论**：**否决**。外部 runtime 的"少维护"收益被语义失真与沙箱失控抵消。

### 2.4 方案 E：AOT 编译到 Go

**否决理由**（ADR-0023 已否决，理由仍成立）：
1. **双重真相源**：MQL 源码 + 生成的 Go 代码两份真相，存储模板需 `findImportedByGoCode()` 启发式匹配——ADR-0023 D1 明确否决。
2. **部署复杂度爆炸**：需要 go build 工具链、插件加载或重新编译、热加载难。
3. **沙箱失控**：生成的 Go 代码有完整语言能力，需额外机制限制——正是 WASM 沙箱试图解决但被否决的问题。

**结论**：**否决**。ADR-0023 的否决理由仍然成立。

## 3. 当前架构的真实瓶颈与优化空间

### 3.1 事实核验结果

本次评审对 VM 热路径做了事实核验，关键发现：

| 位置 | 事实 | 影响 |
|------|------|------|
| `interp.Value`（`interp/value.go:12`） | 80+ 字节 struct：`Kind(1) + Int(4) + Decimal(decimal.Decimal~24) + Str(16) + Bool(1) + Array(24) + Datetime(8) + Class(*8)` | 每次 push/pop 都拷贝整个结构，成本不低 |
| `decimal.Decimal` 内部 | 含 `*big.Int` 指针 | 每次 decimal 运算都有 big.Int 分配 |
| `popN`（`vm_helpers.go:60`） | `make([]interp.Value, n)` 每次 builtin 调用都分配 | 高频分配，GC 压力 |
| `execute` dispatch（`vm_execute.go:82`） | `switch ins.Op` 后二次分发到 `executeStack/executeArith/...` 函数 | 双重跳转，dispatch 开销 |
| `stack` | `[]interp.Value` slice，append 扩容 | 无预分配，push 触发扩容 |
| `locals`（`vm_execute.go:332`） | `make([]interp.Value, NumLocals)` 每次函数调用分配 | 函数调用热路径分配 |
| 常量折叠 | `compile_expr.go` 部分有（`foldIntBinary` 等） | 覆盖不全 |
| 对象池 | 无 `sync.Pool` | Value/args/locals 全靠 GC |

### 3.2 性能瓶颈分析

假设回测 10K bars，每 bar 调用 iMA + iRSI + 几次比较：
- 指令数：~1000 指令/bar × 10K = 10M 指令
- 每指令 ~50-100ns → 500ms-1s 总 VM 时间
- 指标计算：iMA(14) 缓存命中 ~100ns → 10K × 100ns = 1ms

**结论**：指令 dispatch + 栈操作 + 内存分配是真正大头，指标计算因缓存命中占比小。

### 3.3 优化空间分级

| 级 | 优化项 | 预期收益 | 成本 | 风险 |
|----|--------|----------|------|------|
| P0 | 修补 P1 语义风险（`vm-pipeline-deep-audit` §11） | 正确性 | 低 | 低 |
| P1 | `interp.Value` 池化 + `args/locals` 池化 + 栈预分配 | 内存分配 -50%+ | 中 | 低 |
| P1 | `[]func` 跳转表替代 switch（computed goto 等价） | dispatch -20-30% | 中 | 低 |
| P1 | 常量折叠扩展（编译期多折叠） | 指令数 -10-15% | 低 | 低 |
| P2 | 类型特化指令（`PUSH_CONST_INT/ADD_INT` 快路径） | 动态分发 -15% | 中 | 中 |
| P2 | Superinstructions（`PUSH+PUSH+ADD` 融合） | 指令数 -15-20% | 中 | 中 |
| P2 | `decimal.Decimal` 池化或自定义轻量 decimal | decimal 分配 -30%+ | 高 | 中 |
| P3 | 寄存器 VM（若 P1/P2 优化后仍瓶颈） | dispatch -30%+ | 极高 | 高 |

## 4. 架构层面的"更优解"空间

### 4.1 不需要的方向

- **JIT**：开发成本 vs 收益不值得；Go 无成熟 JIT 框架。
- **多后端**：同一 IR 已有 bytecode（生产）+ Go codegen（CLI 调试）——足够。
- **增量编译**：函数级 lazy compilation 意义不大（编译 ~300ms 一次性成本）。
- **WASM**：ADR-0023 已否决，对纯 Go 解释器无安全价值。

### 4.2 真正值得的方向

**核心洞察**：VM 管线的最大风险不是性能，而是**语义边界**——P1 级风险（`isFatalUnimplemented` 一致性、`GetLastError` no-op、Python 隐式全局、`bool(None)` 语义错误、Python 语言检测漏）会让策略行为与预期不符，这比慢 20% 更严重。

**次优洞察**：性能优化应优先做**内存分配**（Value/args/locals 池化）和**dispatch**（跳转表），而非推翻指令集设计。

## 5. 建议路径：方案 F（现状优化）

### 5.1 阶段划分

**阶段 1：语义边界修补（P0，最高优先级）**

按 `vm-pipeline-deep-audit-2026-09-16.md` §11 P1 级风险逐项修复：

| # | 风险 | 建议动作 |
|---|------|----------|
| P1-1 | `isFatalUnimplemented` 注释与代码不一致 | 统一注释与代码：要么改注释（明确 Object/Chart/File 是 fatal），要么改代码（引入 SeveritySkip 分级）。建议改注释+文档，因为 fail-closed 优于 silent skip。 |
| P1-2 | `GetLastError/ResetLastError` 全 no-op | 实现真实 `lastError` 状态：`OrderSend` 失败时写入而非 fatal（或 fatal 但记录 error code 供 `GetLastError` 读）。需权衡 fail-closed 与 MQL4 语义。 |
| P1-3 | Python 隐式全局变量 | 引入函数级局部作用域：编译期追踪 `def` 内变量，非 `self.X` 的赋值进局部槽而非全局。需修改 `pyCompiler.compile` + `resolveVar` 分支。 |
| P1-4 | `bool(None)=true` | 修复 `bool(x)` 解糖：`x != 0` → `x` 的 IsTrue() 语义（None→false, 0→false, 非空→true）。 |
| P1-5 | Python 语言检测漏 `from decimal import Decimal` | `isPythonSource` 加 `from decimal import Decimal` 检测字。 |
| P1-6 | 指标缓存 float64 精度 | 评估是否可接受（已知权衡）；若不可接受，为关键指标（iMA/iRSI/iATR）提供 decimal 参考实现做 parity 测试。 |
| P1-7 | `waitForConfirmation` 强制 confirmed 兜底 | 评估是否可移除（让 barrier 状态机单一真相源）；若必须保留，加注释说明为何绕过。 |
| P1-8 | outcomeUnknown 的 open 路径永久锁仓 | 评估是否需 recovery（open 无 known ticket，可考虑用 clientID 或 magic 匹配）；或明确运维手册说明。 |

**阶段 2：内存分配优化（P1，中期）**

| 优化项 | 具体实现 | 预期收益 |
|--------|----------|----------|
| `interp.Value` 池化 | `sync.Pool` 复用 Value（注意：Array/Class 字段需 deep reset） | 减少 push/pop 拷贝与 GC 压力 |
| `args` slice 池化 | `popN` 返回值用池化 slice 而非每次 `make` | 每次 builtin 调用省一次分配 |
| `locals` 池化 | 函数调用帧的 locals 用池化 | 函数调用热路径省分配 |
| 栈预分配 | `NewVM` 时 `stack = make([]Value, 0, 256)` | 避免 append 扩容 |
| `decimal.Decimal` 池化 | 或评估 `github.com/cockroachdb/apd` 等轻量替代 | decimal 运算分配 -30%+ |

**阶段 3：dispatch 与指令优化（P1-P2，中长期）**

| 优化项 | 具体实现 | 预期收益 |
|--------|----------|----------|
| `[]func` 跳转表 | 每个 opcode 一个 `func(vm *VM, ins Instruction) error`，dispatch 改为 `handlers[ins.Op](vm, ins)` | dispatch -20-30%（Go 无 computed goto，但函数指针跳转表接近） |
| 常量折叠扩展 | 编译期多折叠（`foldDecimalBinary`、`foldStringConcat`、跨指令 peephole） | 指令数 -10-15% |
| Superinstructions | `PUSH_CONST+PUSH_CONST+ADD` 融合为 `ADD_CONST_CONST`；`PUSH_VAR+ADD+STORE_VAR` 融合 | 指令数 -15-20% |
| 类型特化指令 | `PUSH_CONST_INT`、`ADD_INT`、`CMP_INT` 等避免 `Kind` 动态分发 | 动态分发 -15% |

**阶段 4：寄存器 VM（P3，仅当 P1-P3 优化后仍瓶颈）**

仅在以下全部满足时考虑：
1. 阶段 1-3 优化后仍有明确性能瓶颈（profiling 证明 dispatch+栈操作仍占 >30%）。
2. 回测吞吐成为业务瓶颈（多策略并发回测排队）。
3. 有充分成本收益论证（重写 vs 收益）。

**不建议现在做**：收益上限 ~1.3-1.5x，重写+重审计成本极高。

### 5.2 优化优先级排序

```
P0  语义边界修补（阶段 1）           正确性 > 性能
P1  内存分配优化（阶段 2）           收益大、成本低、风险低
P1  跳转表 dispatch（阶段 3 部分）   收益中、成本中、风险低
P2  常量折叠 + Superinstructions    收益中、成本中、风险中
P2  decimal 池化或替代              收益中、成本高、风险中
P3  寄存器 VM                        仅当上述优化后仍瓶颈
```

## 6. 决策矩阵与最终建议

### 6.1 决策矩阵

| 方案 | 是否更优 | 理由 |
|------|----------|------|
| 推翻重写为寄存器 VM | ❌ | 收益上限 ~1.3-1.5x，重写+重审计成本极高，builtin 密集场景收益稀释 |
| 嵌入 goja/starlark/yaegi | ❌ | 语义失真层（MQL→JS/Python 转译），decimal/series 语义需自定义，沙箱边界更难控制，现有投资作废 |
| 回到 Go codegen/WASM | ❌ | ADR-0023 已否决，双重真相源 + 部署复杂度 + 沙箱失控 |
| 树遍历解释器 | ❌ | 性能差 3-10x，失去 Bytecode 核心价值（编译期优化/缓存/覆盖度/fail-closed） |
| **保留架构 + 有针对性优化** | ✅ | 方向正确，修补语义边界 + 内存/dispatch 优化可达 ~1.5-2x 提升，成本可控 |

### 6.2 最终建议

1. **保留当前四段式架构**（CST→IR→Bytecode→Stack VM）——ADR-0023 决策正确，不需要推翻。
2. **阶段 1 优先**：修补 P1 语义边界风险（正确性 > 性能）。
3. **阶段 2-3 跟进**：内存分配优化 + dispatch 优化 + 常量折叠/Superinstructions——预期 ~1.5-2x 提升。
4. **阶段 4 暂缓**：寄存器 VM 仅当前序优化后仍瓶颈时考虑，需充分成本收益论证。
5. **不建议方向**：嵌入外部 runtime、AOT 编译、树遍历解释器、WASM——均已被否决或引入新的失真层。

## 7. 评审结论

**当前 VM 管线不存在"推翻重写"级的更优解**。ADR-0023 的架构决策在当时是正确的，且至今仍然成立：Bytecode 层不是冗余而是核心资产（编译期优化/缓存/覆盖度/fail-closed），Stack VM 的选择是合理的实现复杂度与性能平衡，SDK 唯一出口的沙箱边界比外部 runtime 更易精确控制。

**真正的"更优解"是保留架构 + 有针对性演进**：
- 先修补语义边界（P1 级风险，正确性优先）
- 再做内存分配与 dispatch 优化（收益大、成本低）
- 寄存器 VM 仅作为长期演进选项，需充分论证

**评审判定**：🟡 **条件通过**——架构方向正确，按 §5 分阶段演进即可，不建议推翻重写。
