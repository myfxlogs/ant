# ADR-0028 · 回测可靠性的确定性护栏（自我发现 + 人辅助加固）

- **状态**：Accepted
- **日期**：2026-08-06
- **决策者**：Claude（第一负责人，全责）× 人类负责人
- **涉及功能块**：`mql-compiler`、`backtest-engine`、`strategy-runtime`、`agent-engine`、`api-gateway`、`frontend`、Admin 后台
- **关联**：ADR-0022（盲区架构）、ADR-0023（AST VM）、ADR-0024（Agent 架构）、ADR-0025（Agent UX/经验自进化）、`docs/plan/mql-ea-compatibility-proposal.md` §12

> 本 ADR 回答：**系统能不能自主发现 BUG、修复、自我进化？** 诚实答：**自我发现能自动化（防线抓 bug），修复/加固需要人辅助**——碰钱系统不能把"加规则/改语义"全自动。形态是**确定性护栏（自动发现）+ 人辅助加固/根治**，不是"自我进化闭环"。

---

## 1. 背景：xianhua 事故暴露的本质

用户 `xianhua.chan@gmail.com` 在 2026-08-05~06 连跑 9 次 MACD Sample EA（XAUUSDm 1h），**每次 11 笔交易全部 volume=0**，系统**全部报告 SUCCEEDED**，零警告——"看似成功、实则无意义"的结果，比失败更危险。

**根因（已定位修复）**：EA 代码 `input double Lots = 0.1;` **完全正确**。平台 tree-sitter 对浮点字面量有 quirk，`findIdent` 把参数 Lots 识别成类型名 "double"；编译器又按提案 bug #4 把未定义引用" Lots "静默注册成 =0 的新全局 → OrderSend 用 0 手数下单。**责任 100% 在平台。**

**暴露的本质**：① 平台处理链每一步（解析/编译/VM/SimBroker）都可能错；② 错误被静默吞掉，系统反而报告成功；③ 所有检查都依赖解析器，而解析器本身就是错误源——**没有一道防线独立于平台解读**。

---

## 2. 核心命题（从实证推出）

1. **用户代码可能完全正确，bug 在平台。** "审 EA 源码"抓不到——源码没毛病。正确校验对象是"解析结果自不自洽"和"运行结果合不合理"。
2. **必须有独立于平台解读的防线。** 解析后校验审解析器自身输出；运行后不变量审结果事实（绕过全部解读）。后者本质是"对平台处理链本身的不信任"。
3. **确定性优先。** 找 xianhua 这类错误完全不需要 AI——符号表检查、会计恒等式，100% 确定、毫秒、零 token。**确定性能做的，绝不用 AI。**
4. **诚实上限：80% 方案。** 抓得到参数缺失、不变量违反、已知模式、AI 推得动的根因；抓不到无恒等式可守的纯语义偏差（iMACD 与 MT4 差 0.0001），只能靠对拍 MT golden trace，永远有残差。
5. **预防 vs 检测（本 ADR 选检测）**：让平台"不易错"（预防：属性测试、关键路径形式化）比"抓错"（检测：防线）更根本，但成本高，存量代码不可能形式化重写。本 ADR 走**检测**——对已有代码增量保护、成本合理。但撮合/资金等关键路径应逐步加属性测试（D3 差分/蜕变是预防的雏形），两手都要，检测先行。

## 3. 架构：两道确定性防线 + AI 辅助 + 人辅助加固

```
用户代码 →[解析]→[编译]→[VM]→[SimBroker]→ 结果
            │                        │
      防线 A：解析后校验         防线 B：运行后不变量
      （审解析器输出）            （审结果事实，绕过解读）
            └──── 确定性、免费、自动、永久 ────┘
                        │
      自我发现（自动）+ 人辅助加固/根治（非自动）
```

**防线 A**（编译期，§4.1）、**防线 B**（运行期，§4.2）：确定性、免费、自动、永久留守。

**两条铁律**：
1. **防线 A/B 永远免费自动。** 平台责任，不是增值。
2. **执行语义永不全自动改。** 用户代码改动要用户确认；平台 bug 根治要测试台 + 人 review；**新防线规则要人确认是恒等类（非统计类）才能部署**。

### 自我发现 + 人辅助加固（非"自我进化"）

- **自我发现（真自动）**：防线 A/B 自动抓 bug，确定性，这是能自动化的部分。
- **加固（人辅助，非全自动）**：每出新 bug 形态，AI 提炼候选不变量，但**人必须确认"它真是恒等类（零误报）吗"**才部署——否则 AI 可能把统计类误当恒等类（如把"必须有止损"当恒等式），自动部署会冤枉所有无止损策略。**防线只增不减，方向收敛（恒等类是有限的客观规律），但每条新增需人把关。**
- **根治（人主导）**：root cause 消除按 cadence 批量进行（§5）。

> 诚实结论：这是"自动发现 + 人辅助加固/根治"，不是"自我进化闭环"。发现自动，加固/根治需人——碰钱系统理应如此。

## 4. 防线规则（P0，全部确定性，零 AI）

### 4.1 防线 A：解析后自洽性校验（编译期，CompileToIR/CompileAST 之后）

| 规则 | 检查 | 抓什么 |
|------|------|--------|
| 参数名合法性 | 参数名 ∉ MQL 关键字/类型名 | xianhua（Lots→double）|
| 未定义引用 | 代码引用的标识符必须在 参数表/全局表/内置/枚举 中有定义 | xianhua（Lots 脱节）；连带修提案 bug #4 |
| 参数名唯一 | 参数表无重名 | 多个浮点参数撞名 |
| 入口存在 | OnTick/OnBar/start 至少一个被有效映射 | 经典入口未映射 |

**实现**：遍历符号表（`bc.GlobalSlots`/`bc.Params`/builtin registry）检查；违反即**编译错误**（不静默）。每条规则带正例（合法 EA 通过）+ 负例（构造违反，确认报错）测试。

### 4.2 防线 B：运行后不变量（运行期）

**按"规律性质"分两类，不按"字段"分。** bug 在哪个字段不重要，只要结果违反下列两类规律之一就被抓。两类正交，要同时躲过才漏。

| 类别 | 不变量 | 强度 |
|---|---|---|
| **恒等类**（数学/物理恒等）| 资金守恒、成交手数 >0、价格在 bar 区间（含 gap 容差）、时间单调递增、方向合法、蜕变恒等（周期=1 均线 ≡ 价格、买卖盈亏对称、手数线性）| **判决**：违反即判结果无效 |
| **统计类**（结果反常）| 净值零波动、持仓单调增长、全同向同额、交易频率异常 | **提示**：写入兼容性报告，不阻断 |

**判决 vs 提示**：恒等类违反必是 bug；统计类可能命中合法策略风格（网格/马丁/对冲/剥头皮），只提示。**宁可少判，不可错判**——任何带主观判断的新规则，一律只能进统计类。

**实现决策（关键，且必须带测试）**：
- **资金守恒**：`|期末净值 − (本金 + Σ已实现盈亏 − Σ手续费 − Σswap)| < 容差`。容差取 `max(绝对值, 相对值×本金)`（如 `max(1e-8, 1e-6×本金)`），覆盖浮点累计误差；swap/手续费模型单独测。
- **成交手数 >0**：每笔 `trade.Volume > 0`。
- **价格区间**：`bar.low ≤ open/close ≤ bar.high`，含滑点容差（如 ±spread）。
- **每条恒等类不变量必须带测试**：正例（合法结果通过）+ 负例（构造违反，确认被抓）+ 边界（容差临界）。**恒等类的数学性质零误报，但实现（容差/边界）会错——必须测，不能假设自证明。**
- **判决逻辑**：恒等类违反 → `IsReliable=false` + 结果标"不可信"（接 §4.4）。

**多层叠加**：xianhua 手数=0 被"恒等类（手数>0）"和"统计类（净值零波动）"两层抓住，"资金守恒"反而漏了（手数0→盈亏0→账平）——正因多层，漏一层有兜底。

### 4.3 触发时机：只在回测后

防线 B **每次回测后**触发（真实数据）。**不干跑**——上传时干跑（合成数据跑一遍）的增量只是"上传时就发现、不等用户回测"，但用户上传后迟早回测，回测时防线 B 会跑；干跑却让每次上传都付编译+VM+SimBroker 的算力，对多数正常上传是纯开销，**ROI 太低，砍掉**。防线 A（编译期）已在上传时抓解析错；防线 B 在回测后兜底运行错——足够。

### 4.4 与 assessRisk 的关系：可信度是表现评分的前置闸门

`assessRisk` 已有：基于 maxDD/Sharpe/胜率/盈亏比/交易数产出 Score/Level/IsReliable，评的是"策略好不好"，输入是 Metrics。**垃圾进垃圾出**：结果废了（手数=0）→ Metrics 全 0 → assessRisk 在废数据上评分 → 用户误以为"策略差"，真相是结果无效。

**决策：防线 B 是 assessRisk 的前置闸门。** `buildBacktestResponse` 中防线 B 恒等类必须在 assessRisk 之前执行——不通过则标"结果不可信"，assessRisk 不上场。**复用 `IsReliable` 字段**：语义从"样本够不够"升级为"恒等类通过 + 样本够不够"，不增 proto。

## 5. 修复框架：永久防线 + 择期根治（P2，产品稳定后施工）

**核心认知：修复是两件事。**

### 5.1 两段

| | 永久防线（加恒等类不变量）| 择期根治（改 root cause）|
|---|---|---|
| 保什么 | **正确性**——错误不流出（假成功→诚实失败）| **可用性**——策略真正跑通（诚实失败→真成功）|
| 修的范围 | 修一类 | 修一个 |
| 风险 | 低（只加检测）| 有（改执行语义）|
| 验证 | **恒等类数学零误报，但实现必须带测试（§4.2）**；且**新增需人确认是恒等类**（§3）| 测试台裁决 + 人 review |
| 时效 | 立即（错误当天不流出）| 择期（按 cadence）|

永久防线是永久护栏（不是临时止血）——"手数>0"永远检查，即使 root cause 修了也留。xianhua 的"手数>0"防线比修 findIdent 更重要：抓所有导致手数归零的根因，findIdent 只修一个。**例外**：设计上不支持的（iCustom/DLL/.ex4）只拦（编译期拒绝）、永不根治。

### 5.2 根治 cadence（双周批量 + 归纳同根 + 紧急阈值）

不发现一个修一个。防线兜底让根治不紧急，给"等模式浮现"的底气——同类 bug 出现几次，看清共同根因，一次根治一整类。系统每两周出一份**根治报告**（失败签名聚类 + 影响面 + 建议顺序 + 上期复发率），经营者勾选根治哪些，code agent 批量施工，人 review 部署。**紧急阈值**（如阻塞 >5% 日回测量）打破周期立即触发。周期可调（初期周、成熟月）。

### 5.3 报告与报警

报告在**管理端 Admin"平台健康中心"页**（内部，不给用户，持久化 PG）。报警分层：日常拦截不推（汇总报告）、紧急阈值立即推（邮件/IM + 管理端 SSE）、双周报告轻量通知。复用 `internal/notifier`。先做轻量版，完整运营中心等规模上来再做。

### 5.4 用户代码 bug（告知 + AI 帮补，不替改）

区别于平台 bug：**没有客观答案**（策略好坏依赖意图），代码是用户的（不能替改、有些"缺陷"是故意策略风格）。

**分级响应**：致命（偷看未来/逻辑断裂/手数必0→结果判无效，接 §4.4）；风险（无止损/重仓/马丁/高频→警告，用户确认"故意"即静默）；质量（过拟合/死代码→建议）。

**修复闭环**：`告知（预设文案零 token）→ 提示 AI 补齐 → 用户点 → AI 生成（扣 token）→ 重新过防线 A/B → 版本快照 → 用户 diff 确认 → 应用`。复用 `UpdateStrategyCode`/`CheckAITokenQuota`/agent bridge。**诊断免费、修复收费**——确定性规则绑预设人话文案（零 token 诊断），只有用户点"AI 修"才扣 token。第一期只做确定性缺陷。

## 6. xianhua 完整流转（证明闭环）

1. 上传 MACD Sample → **防线 A**：参数表含保留字 "double" / Lots 引用未定义 → 编译期即报错。
2. （若 A 漏）→ **防线 B 回测后**：volume=0 → 恒等类"手数>0"违反 → 标记不可信（而非 SUCCEEDED）。
3. **永久防线加固**（人辅助）：AI 提炼"成交手数>0"候选不变量 → **人确认是恒等类（零误报）** → 部署 → 从此任何根因的手数归零都被抓。
4. **择期根治**：进双周报告队列 → 人改 findIdent → 测试台（`param_float_default_test`）→ 部署 → 浮点 EA 真正跑通。
5. **结果**：防线永久留守；findIdent 根治后浮点参数不再提错。

## 8. 诚实边界与待验证项

- **谁校验校验器**：防线 A/B 的规则也是代码，也会错（如资金守恒容差设错）。**每条恒等类不变量必须带正/负/边界测试（§4.2）**，不能假设自证明。
- **新防线规则需人确认**：AI 提炼的候选不变量，人必须确认是恒等类（零误报）才部署——否则误把统计类当恒等类，冤枉合法策略（§3）。
- **判决型误报处置**（**设计定档，现在不实现——锦上添花，稳定后再做**）：恒等类实现 bug 或容差偏差可能误报。误报是"防线信号假阳性"，和真 bug 复用同一套双周根治 cadence（真阳性改代码、假阳性改容差）。待实现：产品内反馈入口 + 自动白名单（立即豁免、根治后移除）。现阶段全自助、无客服专线。
- **用户侧恢复路径**：防线判"结果不可信"后用户能做什么（重跑/修代码/看诊断）——前端交互待设计。
- **根治的"人"与 SLA**：现阶段人类负责人；团队扩大后调整。
- **80% 上限**：无恒等式的语义偏差确定性抓不到，靠 MT golden trace 对拍补，永远有残差。
- **MT golden trace 对拍**（**决策：现在不做，成熟期执行**）：解决精度残差（如 iMACD 差 0.0001），优先级低于防线 A/B。成熟期：开发期人工用 MT4/MT5 终端跑标准 EA 导 HTML 入 `testdata/golden/`（proposal §0.18 豁免），复用 `parity_test.go` 扩展为基准（交易级匹配率 + 净利润偏差%），作"平台精度体检"。触发时机：防线 A/B 落地 + 有内测真实用户后。**需人类协助**：到时用 MT 终端导 trace（一次性）。

> ~~进化收敛假设~~ 已澄清：**自我发现自动、加固/根治需人**（§3）——不存在"全自动自我进化"的乐观假设。

## 9. 与其他 ADR 的关系

- **ADR-0022（盲区）**：防线 B 是盲区思想在**结果层**的延伸——盲区查"函数支不支持"，不变量查"结果有没有意义"。
- **ADR-0023（AST VM）**：防线 A 发生在 AST/Bytecode 产生之后。
- **ADR-0024/0025（Agent）**：AI 辅助复用其 agent bridge / 配额；0025 讲 Agent 学经验，本 ADR 讲系统用确定性+人辅助保证可靠。互补不重叠。
- **proposal §12**：本 ADR 把 §12 简化落地为"两道确定性防线 + 永久防线/择期根治"，新增"解析后校验"层与"修复两段论"，并**砍掉低 ROI 的干跑、降调'自我进化'为'自我发现+人辅助'**。
